The Kit Book

Introduction

What a Kit is

A Kit is a focused piece of SlashBuilder’s platform that owns one job and says plainly what it will not do. The App Context Kit owns an app’s identity, its folders for files and settings, test and scratch modes, and a presence entry other apps can read. The Venue (a resource broker) owns machine time on a shared computer. A storage Kit owns where bytes live; an identity Kit owns who is allowed to do what. Each Kit lives in its own repository with its own tests and documentation, and an app is built by composing the ones it needs.

What this repository is

This repository is the book, not a Kit. It is the starting point for using the Kits: it holds this documentation, a set of demo apps that compose Kits, and a Makefile that prepares your computer, runs every test and builds the apps. It never appears in the Kit registry or the catalog, and nothing depends on it.

The Kits themselves are not copied in. make setup downloads each one, at the commit named in kits.lock, into a folder called .kits/. That keeps the Kits’ own repositories as the single place their code changes, and it keeps this book honest: the demos build against exactly the versions the book describes.

How to use this book

  • Read Start here first. It takes you from an empty folder to a running app in four commands.
  • Then read the guides in 20-guides/. The demo apps guide shows the Kits composed into real apps, with measurements of what each Kit saved. The guide on fitting the App Context Kit to other Kits shows where its design meets its neighbours.
  • Reference pages live in 90-reference/: every make target and a glossary.
  • The Kit catalog lives in 30-kits/: a status card for every Kit in the registry, including the ones that are not public yet. See Kits. A Kit’s own reference pages are pulled into the book from the Kit, so you never need its repository to read them; today that is the App Context Kit’s reference, and the others are still to come.

Start here

From an empty folder to a running app. You need make (it comes with the Xcode command line tools on macOS and with build-essential on Debian and Ubuntu) and a way to get this repository onto your computer: either git clone, or the “Download ZIP” button on GitHub. After that, no git is needed: the Kits are downloaded as plain archives.

1. Check your computer

make doctor

This prints a table of the tools the demos need (Flutter and Dart, Rust, a C toolchain, and a few optional ones such as Docker), what it found, and the exact install command for your system where something is missing. It installs nothing, and it fails only when a required tool is missing. Run the commands it prints yourself, then run make doctor again until the last line says everything required is installed.

If you would rather have the tool run the install commands for the required tools, SETUP_INSTALL=1 make setup prints them and asks “y/N” before running anything.

2. Fetch the Kits and the packages

make setup

This runs the doctor, downloads each Kit listed in kits.lock into .kits/ at its pinned commit (printing one line per Kit: fetched, up to date, or skipped and why), then fetches the Dart, Flutter and Rust packages every project needs. It is safe to run again.

While some Kits are private, fetch them too. This needs a GitHub login: install the GitHub CLI and run gh auth login, or set a GITHUB_TOKEN environment variable that can read the repositories.

make setup KITS=all

Without a login, private Kits are skipped with a one-line explanation. A demo app that needs a Kit that was skipped is skipped too, with a line that says which (for example skipped apps/notes_rust: needs storage-kit (private; fetch with KITS=all)); everything else still sets up and tests. The demo apps all need the App Context Kit, so while that is private they cannot be built or tested without a login.

3. Run the tests

make test-fast

This runs every fetched Kit’s own tests, the components in labs/, and the tests of all seven demo apps (the Rust core of notes_rust is tested with cargo test), then prints a table: suite, passed, failed, skipped and seconds. It finishes with OK or FAILED. make test additionally runs the suites that need Docker, Redis or a running daemon, and skips them with a message when the tool is absent.

4. Build and run an app

make app APP=calculator    # a debug build for this computer
make run APP=calculator    # run it (tried on macOS; on Linux the apps build and launch headless in a container, a real desktop has not been tried)
make apps                  # build all seven

The apps are Flutter desktop apps. On macOS this needs the full Xcode app, not only the command line tools; on Linux it needs a few packages (make doctor lists them); the demo apps guide says what the Linux test did and did not show. Windows is not covered.

To see two copies of an app find each other, follow run two copies and watch them find each other.

Running and testing any app

Each app is a standard Flutter project. Desktop runners exist for macOS and Linux; the apps were run on macOS, and on Linux they were built and launched headless in a container (see Linux smoke test). Every command below assumes you are in the repository root, and that you have run make setup once (add KITS=all while the App Context Kit is private) so the Kits the apps depend on are in .kits/.

The Makefile wraps the common cases: make test-fast runs every app’s tests, make app APP=stopwatch builds one app for this computer and make run APP=stopwatch runs it. The plain Flutter commands work too:

cd apps/stopwatch        # or any app
flutter pub get
flutter run -d macos     # run it
flutter test             # run its tests

An app reads its settings from environment variables before it opens. These are the ones that matter. PREFIX is the app’s envPrefix, or the last segment of its id, upper-cased: CALC, MINES, NOTEPAD, STOPWATCH, RENDER_QUEUE, LAUNCHER.

VariableEffect
APP_CONTEXT_SCRATCH=/some/dirPuts the app’s data, config, state, cache and runtime directories, and the roster, under /some/dir. Use it to run without touching your real settings
PREFIX_MODE=mock (or APP_CONTEXT_MODE=mock)Mock mode: the resource-broker session is an in-memory fake, and peers use the fake network
APP_CONTEXT_DEVICE=laptopThe name of this copy for peers. Give each copy its own
APP_CONTEXT_ACCOUNT=homeThe account half of the peer scope key. Default local
APP_CONTEXT_PEERS_DIR=/some/dirWhere copies on one machine announce themselves. Must be the same for every copy
APP_CONTEXT_ROSTER_DIR=/some/dirWhere the app writes its presence file. Beats APP_CONTEXT_SCRATCH
PREFIX_DATA_DIR, PREFIX_CONFIG_DIR, …Override one directory exactly

Details are in the App Context Kit’s specification (spec/APP-CONTEXT.md in that Kit), sections 2 and 6.3.

flutter run -d macos starts the app as a child of the Flutter tool, which passes your shell’s variables on (this is from reading the tool’s source; no window was opened for this page). An app started from Finder or the Dock does not see your shell’s variables.

The macOS sandbox rule. Three apps have the macOS App Sandbox on: calculator, minesweeper and notepad. The other three (launcher, render-queue, stopwatch) have it off. A sandboxed app can only write inside its own container, ~/Library/Containers/<bundle id>/Data/, and that container also has its own HOME and TMPDIR. Two things follow:

  • A path outside the container, such as /tmp/..., in APP_CONTEXT_SCRATCH or APP_CONTEXT_PEERS_DIR does not work for a sandboxed app. With APP_CONTEXT_SCRATCH the app cannot create its directories: the companion shows its startup error screen (the calculator’s first version, before the companion package, crashed with an unhandled PathAccessException). With APP_CONTEXT_PEERS_DIR the process stays up and works alone, and the footer says “Peers: off (peers unavailable: …)” (asserted in a widget test, not seen). Use a path under the container instead, for example ~/Library/Containers/com.slashbuilder.demo.notepad/Data/tmp/ak-scratch. The bundle ids are com.slashbuilder.demo.calc, com.slashbuilder.demo.minesweeper and com.slashbuilder.demo.notepad.
  • The default roster and peers directories are inside the container too. Two copies of one sandboxed app share the container and find each other with no variables set. Two different sandboxed apps have different containers, so they are not expected to share a roster (reasoned, not tested).

The sandboxed apps that use peers, notepad and minesweeper, also need the com.apple.security.network.client and com.apple.security.network.server entitlements; both projects have them in Debug and Release. With only the server entitlement, two copies listen but never connect, and nothing is logged. That observation was recorded in the apps’ development notes (not published) and was not repeated for this page.

Everything about the sandbox is macOS-specific, and the entitlement files are native build files that a running Dart app cannot change. The App Context Kit’s platforms guide has the full table of what each capability needs.

calculator

Folder: apps/calculator.

Exercises. The least an app can ask of the Kit. A four-function calculator with no stored state, written to find the minimum useful adoption.

Run and test.

cd apps/calculator
CALC_MODE=mock flutter run -d macos    # shows a "mock" chip in the app bar
flutter test                           # 32 tests

What the Kit gave it. AppContextKit.run loads app.json from the asset bundle and closes the app once on window close, quit, SIGINT or SIGTERM. AppContextScope supplies the app name for the title. ModeBadge shows the mock and scratch chip. pumpKitApp in the tests runs the app in mock mode under a scratch directory. The Kit also writes a roster entry that nothing in this app reads.

What it still writes itself. Nothing: lib/kit_gaps/ does not exist. The whole of main.dart is:

import 'package:app_context_kit_flutter/app_context_kit_flutter.dart';

import 'ui/calculator_app.dart';

Future<void> main() => AppContextKit.run(manifestAsset: 'app.json', app: (_) => const CalculatorApp());

Did it need the Kit? No. It is the floor: the Kit is nearly free here, and what it gives back is the app name, test isolation and a roster entry nobody reads.

minesweeper

Folder: apps/minesweeper.

Exercises. A game saved to disk (the game in progress, high scores, two settings), and, through the peer layer, handing a game to another copy or playing one board together. It is the case where a state change has to happen on two sides.

Run and test.

cd apps/minesweeper
flutter run -d macos
flutter test                           # 86 tests

This app is sandboxed. To run two copies that find each other, see the walkthrough and use paths under the container. To exercise the handoff without a window, run the probe (below).

What the Kit gave it. The data directory and AppJsonFile for the saved game and scores, SessionSettings for the two settings, ctx.startPeers to find and connect to other copies, PeerJson for the message bodies, PeersIndicator for “This copy / Peers: N”, NotesBanner and ModeBadge.

What it still writes itself. No gap files. lib/coordination/ (329 lines) is the game protocol: the offer, the person’s yes or no, the pull of the board, the confirmation, and the checks that refuse anything inconsistent. That is the app’s meaning and stays the app’s.

A probe, not a window. tool/peer_probe.dart runs the app’s own coordination code without a window, over the real loopback provider. Two probes on one machine, one offering a game and one accepting:

cd apps/minesweeper
dart run tool/peer_probe.dart --scratch /tmp/ak-ms/laptop  --peers /tmp/ak-ms/peers --device laptop  --for 9 --accept &
sleep 3
dart run tool/peer_probe.dart --scratch /tmp/ak-ms/desktop --peers /tmp/ak-ms/peers --device desktop --for 6 --game --offer 1:handoff

A run of exactly this on 2026-10-24 printed, trimmed to the lines about the handoff (the first number is epoch milliseconds):

Did it need the Kit? For handing a game to another copy it needs a way to find and reach that copy, and the Kit supplies it; the protocol that makes a handoff safe, and what happens when a message is lost, is the app’s 329 lines.

notepad

Folder: apps/notepad.

Exercises. One JSON file per note in the data directory, autosave 600 ms after the last keystroke, damaged-file handling, and the close hook that flushes unsaved typing on quit. With peers: syncing notes between copies, including conflicts and notes too large for one message. It is the heaviest user of the hook.

Run and test.

cd apps/notepad
flutter run -d macos
flutter test                           # 63 tests

This app is sandboxed; see the sandbox rule above. Two copies need different APP_CONTEXT_DEVICE values: notepad refuses a peer with its own device id, because two copies with one device id share one notes folder and are one replica.

What the Kit gave it. The data directory, ctx.dataJson('sync.json') and AppJsonFile for atomic JSON files, SessionSettings, ctx.onClose to save the last keystrokes, ctx.startPeers, PeerJson, PeersIndicator, NotesBanner, ModeBadge.

What it still writes itself. One gap file: lib/kit_gaps/blob_pull.dart (79 lines), a chunked transfer for notes larger than one message, pulled part by part over request and reply. It stays because only one app wants it. lib/coordination/ (619 lines) is the sync engine: version vectors, conflict copies, the digest exchange. The hook itself, note_sync_hook.dart, is 29 lines.

A probe, not a window. Two probes over the real loopback provider; the second creates a 300-character note after the first is ready:

dart run tool/peer_probe.dart --scratch /tmp/ak-np/desktop --peers /tmp/ak-np/peers --device desktop --for 7 --create 1:Shopping:300

stopwatch

Folder: apps/stopwatch.

Exercises. A stopwatch with laps and a countdown. Its state is a point in time plus banked time, saved on every change, so it tests the state directory, settings, and a clean quit and relaunch. With peers: one countdown shared between copies, and a “timer finished” signal announced by one copy.

Run and test.

cd apps/stopwatch
flutter run -d macos
flutter test                           # 49 tests

This app is not sandboxed, so /tmp paths work.

What the Kit gave it. The state directory and settings file, ctx.onClose to save, the exit path, test isolation (the “start, lap, relaunch” test is two opens on one scratch directory), ctx.startPeers, PeerJson, PeersIndicator, NotesBanner, ModeBadge.

What it still writes itself. One gap file: lib/kit_gaps/notifier.dart (35 lines), which shows a desktop notification through osascript or notify-send. It is not something the App Context Kit should own. lib/coordination/ (332 lines) is the shared-countdown rule.

render-queue

Folder: apps/render-queue.

Exercises. A session with a resource broker. Each job takes a hold (ctx.venue.withHoldWaiting), runs, and releases it. It tests what the app does when the broker refuses, waits for capacity, or loses the app (a killed app keeps its hold until the lease runs out).

Run and test.

cd apps/render-queue
RENDER_QUEUE_MODE=mock flutter run -d macos   # an in-memory broker that grants 2 holds at once
flutter run -d macos                          # real mode
flutter test                                  # 38 passed, 5 skipped

In real mode, with no broker token configured, the session is a local one with no limit, and the app says so. Connecting to a real broker daemon needs a token and the daemon’s address; the variables are in the App Context Kit’s specification (spec/APP-CONTEXT.md in that Kit), section 3. The daemon is not part of this repository, which is why the real-daemon tests skip. The app’s behaviour when refused is a setting in config.json: policy (wait or failFast), maxWaitSeconds, retrySeconds and leaseSeconds.

What the Kit gave it. The session that hides fake, local and real, withHoldWaiting (retry a refusal for up to maxWait, with cancel), typed refusals, the settings file, ctx.onClose to cancel running jobs and wait for their holds to be released before the session closes, and the roster scan it uses to tell whether another copy of the app is running.

What it still writes itself. No gap files. The app keeps the policy (wait or fail fast) and the words the person reads.

Did it need the Kit? Yes, and this is the clearest case: the one thing it needed from the broker session that the Kit lacked, waiting for capacity, is now in the Kit.

launcher

Folder: apps/launcher.

Exercises. The roster. The launcher lists the apps that are running on this machine, which tests whether a file-based presence list is enough.

Run and test.

cd apps/launcher
LAUNCHER_APPS_DIR="$PWD/.." flutter run -d macos   # also lists the manifests found in apps/*/app.json
flutter test                                       # 24 tests

The launcher is not sandboxed. It sees an app only if that app writes its presence file to the same roster directory. The three sandboxed apps write inside their own containers, so to see apps in the launcher run the unsandboxed ones (stopwatch, render-queue) with the same APP_CONTEXT_ROSTER_DIR as the launcher.

A probe, not a window. tool/rows_probe.dart prints the rows the launcher would show for a roster directory. A hand-made roster directory with one live entry and one damaged file:

mkdir -p /tmp/ak-roster
NOW=$(date -u +%Y-%m-%dT%H:%M:%SZ)
echo "{\"id\":\"com.slashbuilder.demo.stopwatch\",\"instance\":\"a0000001\",\"name\":\"Stopwatch\",\"version\":\"0.1.0\",\"pid\":$$,\"startedAt\":\"$NOW\",\"heartbeatAt\":\"$NOW\"}" > /tmp/ak-roster/com.slashbuilder.demo.stopwatch@a0000001.json
echo '{broken' > /tmp/ak-roster/junk.json
cd apps/launcher && dart run tool/rows_probe.dart /tmp/ak-roster

It printed, on 2026-10-24 (the pid is your shell’s):

running  Stopwatch  com.slashbuilder.demo.stopwatch copy=a0000001 pid=70742 
unreadable: junk.json

A file whose last heartbeat is more than 15 seconds old shows as stale, and a file the launcher cannot parse is listed as unreadable instead of being hidden.

What the Kit gave it. Roster.scan() and RosterRecord (status live, stale or unreadable), the instance id in the file name so two copies of one app are two rows, ctx.venue.nodes() for the node strip, settings, and scratch isolation for the tests.

What it still writes itself. Two gap files, 50 lines: manifest_scan.dart (36), which walks a folder for */app.json because nothing lists installed apps, and pid_alive.dart (14), which asks the operating system whether a pid is alive (kill -0), because scan() reports live for up to 15 seconds after a crash. Each has one user. A pid check does not work inside the macOS sandbox, and a reused pid reads as alive.

Did it need the Kit? For the roster, yes: Roster.scan() and instance ids replaced a 70-line shim (roster_scan.dart) and fixed two copies erasing each other’s entry; the pid check, the app index and the memory of “gone” are still the launcher’s own, and they are most of what makes it a launcher.

notes_rust

Folder: apps/notes_rust. The only demo app with a Rust core, and the only one that uses a Kit written in Rust.

Exercises. The intended shape of an app: a Flutter interface over a Rust core, joined by flutter_rust_bridge. The core (notes_core) stores notes as content-addressed blocks on the Storage Kit and works inside the App Context Kit context that the Flutter side opened. The question it answers is how two halves share one context. The Dart side opens the context once and hands the Rust side a snapshot of it; the Rust side adopts it (an adopt API added to the App Context Kit for this) and so announces nothing, writes no settings, and creates files only under data and state. Notes have a version history (restoring a version writes one small manifest and copies no body). Two copies sync over the App Context Kit’s peer layer: Dart carries the bytes, Rust holds the blocks, checks every hash before storing anything, and reports conflicts with both versions.

Run and test.

make app APP=notes_rust               # needs make setup KITS=all, flutter_rust_bridge_codegen 2.12.0 and, on macOS, CocoaPods
make run APP=notes_rust
make test-fast                        # cargo test (29) and flutter test (19, in-memory stand-in for the core)
make test-integration                 # flutter test integration_test -d macos (10, the real library inside the app)
sh apps/notes_rust/tool/smoke.sh      # launch the built macOS app for 10 s, check what it wrote, SIGTERM it

What the Kits gave it. From the App Context Kit: the directories and instance id (shared with Rust through the snapshot), AppContextKit.run, the config file the Dart side owns and the Rust side only reads, ctx.startPeers and the peer hub. From the Storage Kit: PartitionStore, per-partition de-duplication, hash-verified reads and the fragment trees.

What it still writes itself. lib/kit_gaps/blob_pull.dart (81 lines, copied from the notepad) for moves bigger than one message; in Rust, the head index (the Storage Kit has no mutable store implementation), a verified insert (its put files tampered bytes under their own hash), the child list of a list node, and the flush of the pack before a head moves. lib/coordination/ is 416 lines of Dart; the Rust core is about 1,800 lines (plus 5,130 generated bridge lines).

What it showed. See the app’s README for the measurements, what the bridge made awkward and how the shared context behaved in practice.

Did it need the Kits? The Storage Kit supplied what a notes store is made of; the App Context Kit’s adopt API is what made one app with two runtimes possible without announcing twice. Neither supplied the sync protocol, the conflict policy or the head index.

What the demo apps do not cover

  • One Rust core, not a family. Only notes_rust has a Rust crate and a flutter_rust_bridge dependency; the other six are Flutter on a Dart core. It was built and run on macOS; on Linux it was built and launched headless in a container (see Linux smoke test), not on a real desktop. The bridge was not tried with a Rust-to-Dart stream, hot reload, or a second Rust core in the same app.
  • Two Kits used from Rust, the rest not. notes_rust uses the App Context Kit’s Rust crate and the Storage Kit. Identity, messaging and transport Kits were probed in separate Rust packages in a private repository (the public-safe summary is Fitting the App Context Kit to other Kits), and the other apps’ own sync, conflict handling and large-note transfer are written in Dart. Even in notes_rust the transport is Dart: the peer layer has no Rust half.
  • notes_rust needs a private Kit. The Storage Kit is not public yet, so the app cannot be built from a public clone alone: it needs make setup KITS=all and a GitHub login with access. Without it, make setup, make test and make apps skip the app with one line (skipped apps/notes_rust: needs storage-kit (private; fetch with KITS=all)) and carry on with the other six; the Kit it needs is named in its kits.need file. The App Context Kit’s Rust crate, which the app also uses, is part of the pinned release candidate.
  • No real network. Peers find each other through announcement files and loopback sockets on one machine. That holds for notes_rust too: nothing in it was run on a second machine.

Fitting the App Context Kit to other Kits

The App Context Kit is the root namespace for one running app: identity, directories, settings, a session with a resource broker (Venue), and a way for copies of the same app to find each other. It is not the only Kit an app touches. During its first round of work, six neighbours were probed to find out where the App Context Kit’s design meets theirs.

This page records, for each one: the question, what was built, what it showed, what the App Context Kit does about it, and what is still open and with whom.

How to read the evidence:

  • The probes run in a private repository; the public-safe summary is here. Each probe was a standalone Rust package that exercised a neighbouring Kit directly. You cannot rebuild them from this repository, and this page does not point at them. The numbers below were measured when the page was written.
  • None of this is inside a demo app. No Flutter app calls the Rust App Context Kit crate or any of these Kits through a bridge, so “works in a probe” is not “works in an app”. See what the demo apps do not cover.
  • The one piece that lives in this repository is labs/interface_candidates, the proposed shared UI components. Nothing in the Kit’s own packages depends on it.
  • Numbers come from debug builds on one machine, usually single runs. Latencies are to show magnitude, not to rank anything.
  • Where a page below says “tested”, it was tested while this page was written. Anything else is from the project’s own notes and says so.

Hearth (transport)

The question. Hearth is SlashBuilder’s messaging protocol, with a hub that fans messages out to devices on an account. Can the App Context Kit use it to carry traffic between copies of one app, using topics scoped to the app?

What was built. A prototype adapter, HearthTransport: join(account, app, device), then broadcast, send(device, bytes), recv, leave. It validates ids before anything reaches the wire. It came with 53 tests in eight files (topics, delivery, isolation, presence, request/reply, payload, catch-up, adapter), run against a real local hub and Redis on loopback ports, plus a patched copy of the hub whose topic module changed by about 60 lines. Nothing touched a production service.

Re-run when this page was written: 53 passed, 0 failed (with the 90-second idle-timeout test skipped).

What it showed.

  • The stock hub rejects app-scoped topics. account/<id>/app/<app>/... gets TOPIC_INVALID on subscribe and publish. The hub’s topic grammar is a closed list of four shapes. The patch adds two. Until the protocol’s topic naming is amended, the adapter carries app traffic on the existing broadcast and device topics, marks each message payload_type = ak.app/<app>, and filters at the receiver.
  • The usable payload is 64 KiB minus the Kit’s header. Re-run: a 65,536-byte payload was delivered intact; 65,537 bytes was refused with ENVELOPE_TOO_LARGE and the connection survived. The 1 MiB figure is the cap on the whole envelope; above it the hub closes the connection without an error.
  • The hub does things the Kit must handle itself. It echoes a broadcast back to the sender. Its message id is not a safe correlation key: 1 of 40 replies was already buffered before the requester’s own publish receipt. Subscribing and then catching up can deliver the same message live and in the catch-up page, so de-duplicate on message id. A copy that goes silent with its socket open is noticed only after the hub’s 90-second idle timeout; a killed copy is reported offline in under a millisecond.
  • Rate limits matter for liveness. On one connection, 10 of 25 rapid publishes were accepted (limit 10 per second). Hourly caps of 600 per connection and 6,000 per account were read in the hub’s code, not measured. By that arithmetic a heartbeat every 30 s uses 20% of one connection’s hourly cap, and every 5 s exceeds it.
  • Ordering holds per sender only. 200 messages from one sender arrived 200 of 200, in order. Four concurrent senders kept their own order, but arrival order across senders disagreed with message-id order.
  • Loopback latency is small. Publish to peer receipt: p50 about 1.4 ms, p95 about 2 ms (60 samples, debug build, one machine).
  • Catch-up paging can skip messages. Paging by a millisecond timestamp with a strict comparison skips messages that share a millisecond across a page boundary. With five synchronized senders and one message per page, a run recovered 9 of 40 messages; an earlier run recovered 10 of 40. The count depends on timing.
  • A retention field means two things. The hub reads field 5 of the publish message as a “do not retain” flag. The published schema and the client SDK call it a retention class. An explicit “history” class is silently not stored.

What the App Context Kit does because of it.

  • The peer layer has a provider interface (discover, connect, send, inbound stream). The Kit ships a fake provider and a loopback provider. There is no Hearth provider yet.
  • Payload limits differ by provider, so a provider has to declare its own maximum and send has to fail before the wire when it is exceeded. The App Context Kit’s specification says so (section 6.2). Not built: today the app passes the limit to PeerJson (for Hearth: 64 KiB minus the header).
  • The Kit’s own envelope carries a Kit-owned correlation id and from.device plus from.instance, which is how echo is suppressed. What a Hearth provider must still add: request deadlines, de-duplication across live delivery and catch-up, a no_retain heartbeat no more often than every 30 s, and reconnect.

Message Kit

The question. The Kit’s coordination envelope is {account, app, channel, from, seq, kind} plus an opaque, app-owned payload. Can Message Kit carry it between processes on one machine, and across its remote-provider seam to another machine?

What was built. A mapping of the envelope inside a Message Kit frame (19 mapping tests), a small peer process for local exchange tests (6 tests), a TCP provider of under 200 lines through the remote seam (4 tests), and a test of an oversize message (1 test).

What it showed.

  • The envelope fits without bending either side. The whole Kit message goes inside one Message Kit payload. One header works for Message Kit and for Hearth, with two mappings. They differ in who acknowledges a publish, whether a peer can send a directed message, size limits, rates, retention, and echo.

  • The remote seam has gaps. Several were found and reported to the Kit’s maintainers.

  • The envelope header needs additions, tracked in the specification: an in_reply_to correlation field, a to field for directed messages, a per-message retain hint, and a provider-declared maximum payload checked before the wire. Storage Kit

The question. Storage Kit is content-addressed storage. The App Context Kit names an app by (account, app id). Can that name also name the app’s slice of storage, and is syncing a note between two copies cheap when only a little of it changed?

What was built. A mapping from (account, app id) to a storage partition, so copies of one app on one account share a partition and different accounts never do; a notes model on that partition; and copy-to-copy sync. The “wire” was an in-process call, so this measured bytes and blocks, not network time. Conflict handling used manifest ancestry. The Kit never merges: the app’s resolver chooses between keep-local, take-remote, merged, or defer.

What it showed. Re-run when this page was written, 10 MiB pseudo-random body, two contexts, debug build:

  • Quotas cannot be enforced until Storage Kit can delete.

Identity Kit

The question. Identity Kit has service principals with scopes. Can the App Context Kit’s admit(peer, hello) hook use them to decide whether a peer may join an app’s coordination: accept, accept read-only, or reject?

What was built. An admit module with scopes app:<id>:run, app:<id>:coordinate and app:<id>:storage. coordinate is accept, run alone is read-only, storage alone is refused. An in-memory fake issuer stood in for issuance, which Identity Kit does not have yet. The fake is a test double, not a design for the real one.

What it showed.

  • The shape works. A program that only types an app id is refused. One app’s principal cannot join another app. A principal from another account is refused. A household rule (a child account may not run a given app) can be checked at each join, so changing a role takes effect without reissuing anything. Identity Kit keeps role out of the principal on purpose, so that rule can only live in whoever verifies.
  • Gaps in Identity Kit: issuance, signing and verification are not built; the principal carries no account; scopes are opaque strings with no constructor or parser; the family graph is not built, so the role rule cannot read real roles.

What the App Context Kit does because of it. The Kit’s only authenticators are an open one that accepts everyone and a shared-secret one marked as a test fake, and the code says plainly that they are for one machine and tests, never a network. The loopback provider has no encryption or authentication; do not use it across a trust boundary. A real authenticator waits on Identity Kit issuance and signing. Until then the App Context Kit scopes copies by account and app id as a naming convention and does not authenticate them: do not treat peers as trusted.

Venue

The question. Can an app hold a reservation on a shared machine the same way whether Venue is real, absent or faked?

What was built. A session type in both languages (Dart and Rust) and the render-queue demo app, which uses it harder than the others.

What it showed. The session hides the three cases. Cross-cutting

Three themes recur across the probes.

  1. Most of what makes the Kit hard lives in the other Kits. The Kit’s own part (find, connect, route) held on the first try in three very different apps. The gaps were payload limits, topic grammar, identity and signing, and storage lifecycle.
  2. App identity is a naming convention until the Identity Kit issues and verifies capabilities. Hearth, Storage Kit and Identity Kit each showed a different face of the same fact.
  3. Build a shared piece when the second app copies it, not before. The same rule decided what moved into the Kit (a wait helper, JSON helpers, a peers handle) and what stayed out (single-user helpers).

App Context Kit

  • Registered Kit: no, so it is not in the catalog
  • Source: not public yet

The App Context Kit is the root namespace for one running app: its identity, its folders for files and settings, test and scratch modes, a roster entry other apps can read, a session with a resource broker, and an opt-in way to find other copies of the app. The seven demo apps in this book are built on it (six are Flutter on a Dart core; notes_rust is a Flutter UI over a Rust core that shares the UI’s context through the Kit’s adopt API), and the demo apps guide measures what it saved and what it still leaves for an app to write. Its name is final, and it is a candidate for the registry rather than a member of it.

Its own reference documentation is pulled into this book from the Kit, at the commit this book pins (make docs-pull), so you can read it without access to the Kit’s repository. It is the only Kit pulled so far. Start at the reference index.

  • Status: alpha (what this means)
  • Language: Rust
  • Kind: hybrid
  • Has real code today: Yes
  • Source: slash-builder/inference-kit

What it owns

Inference Kit is a cross-platform inference service for Hearth household clusters. Apps declare model dependencies (semantic versions); Inference Kit resolves, loads, and caches model weights via Storage Kit (shared across apps, mmap’d RO).   • Output safety gates (application-layer concern)
  • Model-specific tuning (quantization strategy is app config, not Inference Kit)
  • Cloud hub relay in MVP (future feature gate; local-only MVP)
  • TPM attestation (optional future enhancement; not MVP)

Venue Kit

One registry and planner for every place work can run.

  • Status: alpha (what this means)
  • Language: Rust
  • Kind: cross-platform
  • Has real code today: Yes
  • Source: not public yet
  • Name: provisional; it may change

What it owns

Venue Kit describes and plans over the places work can run: a machine, a VM, an API provider, a cloud pool you can rent from, a peripheral behind a host. What each is, how to reach it, what it has, what it can do, what it will accept, what it costs, and who may use it. It is a Kubernetes Resource Model vocabulary rather than a new format: Node, Endpoint, NodePool, ContractClass, ContractClaim, Placement and Budget in the API group node.slashbuilder.com/v1alpha1, with PriorityClass and Lease accepted verbatim from Kubernetes. Kubernetes (and DRA, Karpenter) is treated as the standards body: its names, shapes and semantics are followed unless a divergence is recorded with a reason.

Every answer is Yes, No or Unknown, and an Unknown says what would settle it. Nothing is trusted because a document says so: each manager writes its own observation, the effective view is computed on read and keeps disagreements visible, and work that carries data classes needs both a use grant and the data owner’s egress grant or the answer is Unknown.

What it will not do

  • Running the work, or provisioning anything: Venue plans and records, something else provisions
  • Inference, storage, messaging: those are their own Kits, which sit on top of or beside this one
  • Containers and other workloads (many, short-lived; their names and images describe the estate): another layer’s job
  • Changing a machine: accounts, keys, sudo, packages, policies.

The short version of the results

  • One contract, two implementations. Dart and Rust pass the same 61 fixtures. The second implementation found about a dozen behaviours the first had decided silently.
  • Less code per app. Helper code the six apps wrote themselves went from 727 lines to 330, up to 777 after coordination was added, and down to 164 once the repeated parts moved into the Kit. Every main.dart is 5 to 11 lines. Build a Kit piece when the second app copies it, not before.
  • The hook is the right shape, and not enough on its own. It carried a shared timer and a game handoff cleanly, and live play only just. For sync it was a small shell around a lot of app code, because the Kit gives no acknowledgement, large transfer, replay or liveness tick.
  • Same-machine coordination works; across machines is not built. Two copies found each other in under half a second on one machine; a crashed copy disappeared in about 3.5 s.

What is not verified

A real Linux desktop session (the cores are tested in Linux containers, and the demo apps were built in release mode and launched headless in a Linux container), window close on a real window, signed or packaged release builds, Windows beyond the pure path rules, and the peer code against a real remote hub. Each page marks its own unverified claims. “Verified” in these pages means a test, a command or a measurement in the App Context Kit repository; anything else is labelled as reasoned or reported.

Overview

Reference page pulled from app-context-kit at commit 4797e81. Edit it in the Kit, not here.

The App Context Kit is a small library that gives one running application its root namespace: who it is, where its files live, where its settings are, whether it is running for real or under test, who else is running, and how it shuts down. You describe the app in a short app.json, open an AppContext, and the rest of your code asks that object instead of working these things out itself.

It is a work in progress. App Context Kit borrows its idea from the BeOS Application Kit; it is not a reimplementation of it and is not affiliated with Haiku. Nothing here is published to a package registry. See Status.

The problem

Every desktop or mobile app starts main() by answering the same questions, and most answer them differently:

  • Identity. What is this app called, what version is it, and what is its reverse-DNS id? The answer ends up in four places that can disagree: the pubspec.yaml, the macOS bundle, the Linux runner and a string in the code.
  • Where files live. Data, settings, cache and runtime files each have a conventional home on macOS, Linux and Windows. Apps hard-code one of them, or copy a path helper from the last project.
  • Settings. Reading and writing a small JSON file safely: atomically, and without overwriting a file you could not read.
  • Test modes. A way to run the app against fakes, in a throwaway folder, without touching the developer’s real data. Each app grows its own --mock switch.
  • Who else is running. Is another copy of this app already open? Which apps are running at all?
  • Quitting cleanly. Window close, Quit and Ctrl-C are different events. Cleanup that runs on one of them is often skipped on the others.

None of this is hard. It is the same code, written again for each app, and it is where small bugs live: a settings file that is silently replaced after one bad byte, a lock file left behind after a crash, a test that wrote into the real home directory.

The idea

Put all of it in one place, under one object, driven by one file.

app.json  ->  AppManifest  ->  resolve (pure function)  ->  AppContext.open  ->  your app

Resolution (which directory, which mode) is a pure function of the manifest, the platform, the home directory and the environment. It does no I/O, so it can be specified exactly and tested with fixtures. Opening a context then creates the directories, reads the settings, opens a Venue session and announces the app in the roster. Closing it undoes that, in a fixed order, once.

Where it comes from

The idea and the shape come from the BeOS Application Kit. In BeOS every program had a BApplication object that was the program’s root, and a BRoster that knew which programs were running. This Kit keeps those two ideas: one root object per running app, and a roster of running apps.

It differs on purpose in three ways:

  • No looper or handler model. BeOS built the Kit around message loops (BLooper, BHandler). This Kit does not own your event loop or your threads. Flutter already has one. The Kit gives you a context object, and the only messaging it provides is the opt-in peers piece, between copies of the same app.
  • Cross-language. The contract is a written spec plus shared test fixtures, not one implementation. A Dart implementation and a Rust implementation both pass every fixture.
  • Flutter on top of a Rust-or-Dart core. The intended shape is a Flutter UI over a core that may be written in either language. Today six of the demo apps (in The Kit Book) use the Dart core, and a seventh puts a Rust core under a Flutter UI. The Rust crate implements the same spec and passes the same fixtures, and the two sides share one context: the Dart side opens it and the Rust side adopts it (see Sharing one context with a Rust core).

Venue is a resource broker. An app asks it for a lease on something, such as a slot to run a job, holds it while it works and releases it. The Kit does not implement Venue; it provides the client side and hides whether a Venue is configured. With no Venue the session is local and says so, and in mock mode it is an in-memory fake. The client for a real daemon exists in the Dart core only: the Rust crate has local and fake sessions and no remote Venue session.

Peers are off unless the manifest lists "peers" in its kits. The Kit ships two providers: an in-memory fake network for mock mode and tests, and a loopback provider for copies on one machine. Peers between machines are not part of the Dart core.

A Flutter companion package, app_context_kit_flutter, adds what the pure-Dart core cannot do: load app.json from the asset bundle, close the context exactly once however the app ends, and a few small widgets (a mode badge, a notes banner, a peers indicator, a startup error screen). It also provides widget-test helpers.

Design rules

  1. The spec is the contract. spec/APP-CONTEXT.md and the fixtures in spec/conformance/ define behaviour. Both implementations must pass every fixture. If the prose and a fixture disagree, the fixture wins and the prose is corrected.
  2. Apps compose the Kit and never fork it. An app that needs something the Kit lacks writes it in the app (the demo apps keep these under lib/kit_gaps/) and marks it // KIT GAP:. That code is the record of what is missing.
  3. The Kit never interprets an app’s payload. It finds peers, connects to them and carries bytes. What a message means is the app’s decision.
  4. The core stays pure Dart. app_context_kit has no Flutter import. Anything that needs Flutter goes in app_context_kit_flutter.
  5. Build a piece when the second app copies it. Code only one app needs stays in that app. A helper moves into the Kit once a second app has written the same thing.

What it does not do

  • No UI toolkit. The companion package has a handful of plain Material widgets for the Kit’s own state. It has no design system, theming, routing or state management.
  • No sync engine. Peers gives you discovery, a connection and best-effort ordered delivery. Reconciling data between copies is your code. Large transfers are not built.
  • No installer or updater. The Kit does not install, update or launch apps. The roster reports which apps are running, not which are installed.
  • No authentication or accounts. The peers scope key is (account, app id), and the account defaults to the string local. The default authenticator, OpenAuthenticator, accepts every peer, so an account or app id is a claim, not a proof. The only other authenticator in the code is a test fake. The Kit does not issue accounts or credentials.
  • No window title, bundle id or version sync. Those live in native build files that a running app cannot change. A script, dart/app_context_kit_flutter/tool/check_identity.dart, checks that they agree with app.json.

This guide takes you from an empty folder to a Flutter desktop app that runs on the App Context Kit, then shows the same thing in plain Dart and in Rust. For what the Kit is, read the overview. For every field and rule, see the context guide.

The app you build is a window with a button. Each tap is counted, saved as a setting and written to a file. The finished project is in docs/examples/flutter_hello/. Every code block below is a file from that directory, or a file from docs/examples/dart_cli/ or docs/examples/rust_cli/.

4. Write main.dart

AppContextKit.run does the work a hand-written main() would: it initialises Flutter’s binding, loads and validates app.json from the asset bundle, opens the AppContext, mounts an AppContextScope above your widget, and makes window close, Quit, SIGINT and SIGTERM all close the context exactly once before the process ends. 5. Read the context, save a setting, write a file

Create lib/hello_app.dart. This is docs/examples/flutter_hello/lib/hello_app.dart:

import 'package:app_context_kit/app_context_kit.dart';
import 'package:app_context_kit_flutter/app_context_kit_flutter.dart';
import 'package:flutter/material.dart';

class HelloApp extends StatefulWidget {
  const HelloApp({super.key});

  @override
  State<HelloApp> createState() => _HelloAppState();
}

class _HelloAppState extends State<HelloApp> {
  late final AppContext ctx;
  late final SessionSettings settings;
  late int taps;
  var _started = false;

  // An InheritedWidget cannot be read in initState, so read the context on the first didChangeDependencies.
  @override
  void didChangeDependencies() {
    super.didChangeDependencies();
    if (_started) return;
    _started = true;
    ctx = AppContextScope.of(context);
    settings = SessionSettings(ctx.config);
    taps = settings.get<int>('taps', 0);
  }

  void _tap() {
    setState(() => taps++);
    settings.set('taps', taps); // a setting, in <config>/config.json
    ctx.dataFile('taps.log').writeAsStringSync('$taps\n'); // a file, under <data>
  }

  @override
  Widget build(BuildContext context) => MaterialApp(
        title: ctx.manifest.name,
        home: Scaffold(
          appBar: AppBar(title: Text(ctx.manifest.name), actions: [ModeBadge.forContext(ctx)]),
          body: Column(children: [
            NotesBanner.forContext(ctx),
            Text('Taps: $taps'),
            FilledButton(onPressed: _tap, child: const Text('Tap')),
          ]),
        ),
      );
}

What this uses:

  • AppContextScope.of(context) returns the AppContext that AppContextKit.run mounted. It throws a FlutterError that says how to fix it if there is no scope above the widget. There is also maybeOf, which returns null.
  • ctx.manifest is the parsed app.json.
  • A setting. ctx.config is a ConfigStore over <config>/config.json. ctx.config.set('taps', 3) saves at once, atomically. If config.json is damaged, set throws DamagedConfigError rather than overwrite a file it could not read. This example wraps the store in SessionSettings, whose set never throws: while the file is damaged it keeps the change in memory for the session, and settings.readOnly tells you so. See settings.
  • A file under data. ctx.dataFile('taps.log') is a File under ctx.dirs.data. The directory already exists. For a JSON file with an atomic write and a read that tells “missing” from “damaged”, use ctx.dataJson('name.json').
  • ModeBadge.forContext(ctx) shows nothing in a normal run and a chip reading mock, scratch or mock + scratch otherwise.
  • NotesBanner.forContext(ctx) shows warnings and errors the Kit recorded in ctx.notes, such as a damaged settings file. It hides information-level notes.

ctx.notes is a plain list that notifies nobody. If your app adds a note, rebuild the banner yourself.

Scratch and mock

Two environment variables let you run the app without touching real data:

  • APP_CONTEXT_SCRATCH=<folder> puts every directory, and the roster, under that folder.

7. Venue, and the default

Venue is a resource broker. ctx.venue is the one object an app uses to ask it for something. The manifest’s venue.mode decides how the Kit opens it:

venue.modeBehaviour
offNever looks for a token or a daemon. The session is local, with the description Venue: local (Venue is off for this app).
auto (the default)Looks for a token. With none, the session is local: Venue: local (Venue not configured). With a token, it connects if the daemon answers; if not, it degrades to local and records a warning.
onThe app needs Venue. With no token, or no answer, opening the context fails, and the Flutter companion shows the error screen with the code venue-required.

So an app does not need a Venue to run, and does not need "mode": "off" for that: auto already degrades to a local session when nothing is configured. This example sets off to say plainly that it does not use Venue. In a normal run the Kit records one information-level note carrying the Venue description. NotesBanner hides it unless you pass showInfo: true.

In mock mode the session is always the in-memory FakeVenue, whatever venue.mode says. The environment variables that configure a real Venue are in the context guide.

macOS sandbox

The macOS runner that flutter create generates has the App Sandbox on. Three things follow, each checked on macOS with a project built as above.

Files go in the app’s container. Inside the sandbox, HOME and TMPDIR point into ~/Library/Containers/<bundle id>/Data, so the default directories and the roster all land there. You do not need to do anything.

A scratch folder must be inside the container too. The sandbox refuses writes elsewhere. With APP_CONTEXT_SCRATCH=/tmp/somewhere, the app created nothing and showed its start-up error screen: “This app could not start. The app’s folders could not be created or read: Creation failed (/tmp/somewhere)”, with Error code: open-failed. A path under the container works:

APP_CONTEXT_SCRATCH="$HOME/Library/Containers/dev.example.hello/Data/tmp/scratch" flutter run -d macos

The container folder only exists after the app has run once.

Network access needs an entitlement. flutter create writes these files in macos/Runner/: DebugProfile.entitlements (sandbox, JIT and network.server) and Release.entitlements (sandbox only). A Venue daemon is reached over HTTP, and peers connect to each other, so an app that does either is likely to need outgoing connections allowed. Add this to both files:

<key>com.apple.security.network.client</key>
<true/>

For reference, in release builds the calculator demo app (Venue off, no peers) declares the sandbox and nothing else, and the notepad demo app (peers on) declares network.server and network.client. What happens to an app that uses peers or Venue without these entitlements was not tested. Two of the demo apps, launcher and render-queue, turn the sandbox off.

fn main() -> Result<(), Box<dyn std::error::Error>> {

        println!("launches {launches}");

    Ok(())
}

A missing file is an empty store, not a problem. A damaged file is one that is not valid UTF-8, not valid JSON, not a JSON object, or cannot be read. AppContext.open still succeeds, problem says why, a warning note is added, and every write is refused until you decide what to do. The file is never replaced silently (spec section 5, item 3).

setAsideCorrupt() is that decision. It renames the file to config.json.corrupt (replacing an older .corrupt copy), empties the store, clears problem and returns the new File. It returns null when nothing was damaged. The damaged content is kept, never deleted. If you want the person to choose, show them problem and call it from a button.

Each copy of an app keeps its own in-memory values and rewrites the whole file on set. Two copies running at once can overwrite each other’s keys, and the Kit takes no lock. This follows from reading the code; there is no test for it.

SessionSettings

SessionSettings(ctx.config) wraps a ConfigStore for UI code that should not throw when the file is damaged.

  • While the file is healthy it is the store: set saves, get reads the file’s values.
  • While the file is damaged, set keeps the value in memory for this session only and never touches the file. get returns that session value, then the file’s value, then the fallback. readOnly is true, so you can tell the person their change will not be kept.
  • After setAsideCorrupt() on the store, readOnly is false and writes reach the file again. Values set during the damage are not written then.

SessionSettings.set never throws DamagedConfigError. It can still throw FileSystemException if the disk refuses a write.

The Venue session

ctx.venue is a VenueSession. Its kind is local, fake or venue; isConnected is true only for venue; description is one sentence. The same calls work for all three, so app code does not branch. The wire details (the daemon’s HTTP API) belong to Venue, not to this Kit; spec section 3 and section 5, items 2, 6 and 7.

CallMeaning
hold(need, {leaseSeconds: 300})Ask for something. A VenueNeed has name, contractClass and parameters. Returns a VenueHold
start(hold), renew(hold), release(hold)The hold’s life cycle
holds()This consumer’s own live holds, for finding orphans after a crash
nodes()The nodes Venue knows about
withHold(need, body, {leaseSeconds, onLeaseLost, renewEvery})Hold, start, renew in the background while body runs, then release, also on error. renewEvery defaults to a third of the lease. withHoldWaiting(need, body, {required maxWait, retryEvery, cancel, onWaiting, ...})Like withHold, but retries a refusal until maxWait has been spent in naps of retryEvery. maxWait: Duration.zero is withHold. Completing cancel ends the wait with HoldWaitCancelled

Refusals are typed. VenueRefused carries a kind: doesNotFit (HTTP 409; retrying later can succeed) or forbidden (HTTP 403). VenueRefused.retryable is true only for doesNotFit, and plainReason unwraps the daemon’s JSON error message. VenueUnavailable is everything else: a transport failure, a timeout, 401, 5xx. It carries the HTTP status when there was an answer.

withHoldWaiting retries forbidden only while holds() shows this consumer still has live holds, because the daemon uses the same status for “over your live-hold limit” and for “no grant”. This is a heuristic and the spec records its known failure: a consumer that holds something and lacks a grant waits the full maxWait for nothing. See spec section 7.

The three sessions:

  • LocalVenue(why): no Venue. Work still runs. Holds exist in this process only, so two apps can both “hold” the same thing, and a second hold with the same name in one process is refused as doesNotFit.
  • FakeVenue({capacity: 1}): in memory, one node. It refuses a hold when capacity holds are live, keeps a log of calls (hold <name>, start <name>, renew <name>, release <name>), and refuseNext(n, {kind}) makes the next n holds refuse. Use it in tests.
  • RemoteVenue (Dart only): the daemon over HTTP with a bearer token. IoTransport does the HTTP; with VENUE_DAEMON_FINGERPRINT it trusts exactly one certificate and no authority. A fingerprint that is not 32 bytes of hex, or a certificate that does not match, is reported as VenueUnavailable with an explanation. Pass your own DaemonTransport to AppContext.open(transport: ...) to supply replies without a socket.

Lifecycle

Open

AppContext.open(manifest, {env, platform, home, transport, announce, heartbeat, fakeCapacity}) does these steps in this order:

  1. Resolve (may throw ResolveError).
  2. Create the five directories (may throw FileSystemException).
  3. Open the settings; add a warning note if damaged.
  4. Open the Venue session; add its note. In venue.mode: on, this step throws VenueUnavailable if Venue cannot be used. Nothing has been announced yet, so nothing is left behind.
  5. Draw this copy’s instance id: eight random lower-case hex digits.
  6. Write the roster entry and start the heartbeat, unless announce: false. If that fails, Venue is closed and the error is rethrown.

announce: false is for tests and tools that should not appear in the roster. heartbeat (default 5 seconds) is how often the roster entry is refreshed.

Run

AppContext.run(manifest, body, {...}) is open, then body(ctx), then close, also when body throws. If body throws, that error is what you get; a failure while closing is recorded as an error note instead of replacing it. If body returns and closing fails, run throws the AppCloseError.

run closes the moment body returns. That suits a command-line tool. It does not suit a Flutter app, where runApp returns at once; use AppContextKit.run there.

Close

ctx.close() does these steps in this order and always does all of them:

  1. Stop the heartbeat and delete this copy’s own roster entry (only that file).
  2. Run every ctx.onClose hook, last added first. A hook may be async; each is awaited. Peer hubs made by ctx.peerHub or ctx.startPeers are closed by a hook of their own, so they follow the same order.
  3. Close Venue, last, so a hook can still use it.

If any step threw, the errors are raised together afterwards as one AppCloseError (its errors and stackTraces lists hold every failure). A failing hook never stops a later hook or the Venue close.

close() is idempotent. A second call, even a concurrent one, runs nothing again and returns when the first has finished. Only the first caller sees an AppCloseError.

Register hooks with ctx.onClose(() async { ... }). Typical uses are flushing unsaved edits and closing your own resources. The notepad demo app registers its flush hook after starting peers, so on quit the last keystrokes are saved and announced while the hub is still open.

Sharing one context with a Rust core

A Flutter app with a Rust core must not open the context twice: it would be in the roster twice, under two instance ids, and two code paths would write one config.json. The Dart side opens the context (AppContextKit.run) and hands the Rust side a snapshot; the Rust side adopts it. The full rule is spec section 8.

Dart, the owner. ctx.snapshot() returns a map {schema, appId, instance, mode, scratch, dirs: {data, config, state, cache, runtime}, roster} you can jsonEncode and pass over the bridge. It has no secrets and no handles, and asking for it announces nothing.

Rust, the adopter.

#![allow(unused)]
fn main() {
let snapshot = ContextSnapshot::parse(&json_from_dart)?;   // strict: unknown schema, missing field, relative path are errors
let ctx = AppContext::adopt(&snapshot);                    // no roster entry, no heartbeat, no config.json written
let blocks = ctx.create_data_dir("blocks")?;               // directories under data and state only
let file = ctx.data_file("heads.json")?;                   // a path under data (no `..`, nothing created)
let theme: String = ctx.settings().get_or("theme", "light".into());  // read-only: `set` and `save` return Err(ReadOnly)
}

One owner per file. The owner (the side that opened the context) owns config.json and the roster entry. The adopter reads settings, never writes them, and owns the files it creates under data and state. A setting the Rust core wants changed is a request to the Dart side. After the owner changes a setting, ReadOnlySettings::reload() shows it.

The roster

The roster answers “who is running?”. Each running copy writes one JSON file into the shared roster directory (see directories) and refreshes it.

  • File name: <ID>@<INSTANCE>.json, for example com.slashbuilder.demo.calc@1a2b3c4d.json. The instance is eight lower-case hex digits, drawn at random per opened context.
  • Content: id, instance, name, version, pid, startedAt and heartbeatAt (UTC, ISO 8601). ctx.instance is this copy’s instance id.
  • Heartbeat: the file is rewritten every 5 seconds (heartbeat:), through a temporary file and a rename. A failed heartbeat is recorded in RosterAnnouncement.lastError and does not stop the app.
  • Two copies of one app are two files. Withdrawing one removes only its own.
  • Stale: an entry whose heartbeatAt is more than 15 seconds old (staleAfter:) is stale. A copy that exited cleanly deletes its file. A copy that crashed leaves it behind, and the Kit never deletes it.

Reading it, on ctx.roster (or Roster(dir)):

CallReturns
running()RosterEntry for every live entry. Stale and unreadable files are skipped, not deleted
scan()A RosterRecord for every *.json file, sorted by id then instance, with a status: live, stale or unreadable

A RosterRecord has file, status, entry (null when unreadable), id and instance. For an unreadable file, id and instance come from the file name, so it can still be attributed. Use scan() to tell a crash (stale) from “never ran” (no record) from a damaged file (unreadable). A file named <ID>.json with no instance part, from before instance ids existed, has a null instance. parseRosterFileName(name) splits a name; the id contains dots, so it splits at the last @.

The PID in an entry means something only on the same machine and for the same user. The roster does not check that the process is alive; it trusts the heartbeat.

Spec: section 4 and section 5, item 5. The spec asks whether the roster belongs in the Kit, in Venue or nowhere; the Kit keeps the smallest version so that use can answer.

Peers

Peers are other running copies of the same app for the same account. They are opt-in: list "peers" in kits, or ctx.peerHub and ctx.startPeers throw KitNotDeclared. This guide covers only how the context supplies them; the design is in spec sections 6 and 7.

  • Who this copy is: ctx.peerAccount (APP_CONTEXT_ACCOUNT, else config account, else local), ctx.peerDevice (APP_CONTEXT_DEVICE, else config device; generated once as d- and eight hex digits and saved, or kept for this run only if the settings file is damaged) and ctx.instance. The first call to ctx.peerDevice writes device to the config file.
  • Provider by mode: an explicit provider if you pass one to peerHub; in mock mode, an in-memory fake network (pass one FakePeerNetwork to several contexts to make them see each other); otherwise the loopback provider over ctx.peersDirectory (APP_CONTEXT_PEERS_DIR), which finds copies on one machine.
  • ctx.startPeers(hook, {network, options}) builds and starts a hub and never throws for a runtime condition. It returns a PeersHandle at once: hub (null when peers are unavailable), started (a future that completes when the hub is open or has failed, never with an error), error (a sentence starting peers unavailable: ), isStarting, isRunning and changes (a broadcast Stream<void> that fires when the hub opens or fails and on every peer change). handle.hub?.broadcast(...) is always safe. KitNotDeclared is not swallowed: that is a bug in the app.
  • ctx.peerHub(hook, {provider, network, authenticator, options}) builds a hub without starting it; call hub.start(). Use it for a custom provider or authenticator.
  • The hook is an AppCoordination that you write: channel, hello(), admit(peer, theirHello), onPeer(peer, change), onMessage(from, message) and an optional attach(hub). The Kit never reads a payload; it carries bytes and an app-declared schema integer.
  • PeerJson has helpers for JSON payloads: encode, decode (null on malformed input, never throws), fits, encodeWithin (throws PeerPayloadTooLarge), quiet and label. AppMessage.jsonBody decodes a message body.

Hubs are closed with the context. The default authenticator accepts every peer.

Venue guide

Reference page pulled from app-context-kit at commit 4797e81. Edit it in the Kit, not here.

How an app built on the App Context Kit asks Venue for a share of a machine’s resources, and what happens when Venue says no, goes away, or the app dies.

Venue is a resource broker: an app asks it for a hold (a reservation of some capability, for example “run a container”), and Venue grants it, refuses it, or takes it back when the lease runs out.

This guide covers the Kit’s Venue session in Dart and Rust. The Kit’s Rust crate has no remote Venue session: it has the local and fake sessions only, so everything below that talks to a daemon (the venue session, pinned TLS) is Dart only. The rules behind it are in spec/APP-CONTEXT.md (sections 3, 5 and 7). Each snippet below was run: against the mock session, against the local fallback, and against a throwaway Venue daemon (see Testing against a daemon). The daemon is not part of the App Context Kit repository.

The session

ctx.venue is a VenueSession. It has three implementations, and app code calls the same methods on all of them.

kindWhen you get itWhat a hold means
venueA daemon answered and a token was found (Dart only: the Rust crate has no remote session)A real reservation. Other apps on the machine are held to the same limits.
localVenue is off, not configured, or not reachable (and the manifest allows that)A bookkeeping entry inside your process. Nothing stops another app, or another copy of yours, from “holding” the same thing.
fakeMock mode (APP_CONTEXT_MODE=mock)An in-memory node with a fixed capacity, for tests.

ctx.venue.description is one sentence saying which you got, for example Venue: local (Venue not configured). The context also puts it in ctx.notes, with severity warning when Venue was expected but could not be used. Show it somewhere. The local session gives no cross-app protection, and the person using the app should be able to tell.

Hiding the difference is the point: the app has one code path. The cost is the local row above. The session cannot make a promise only a daemon can keep, so it tells you instead.

How a session is chosen

The manifest (app.json) has an optional venue block:

{

  "name": "Render Queue",

The context decides in this order and stops at the first step that applies.

  1. Mock mode (APP_CONTEXT_MODE=mock, or <PREFIX>_MODE=mock): always the fake session, whatever venue.mode says.
  2. venue.mode is off: always local, with the description “Venue is off for this app”.

Token lookup

First match wins:

  1. VENUE_TOKEN: the token itself.
  2. VENUE_TOKEN_FILE: a path to a file holding the token.
  3. <config>/venue-token, where <config> is the app’s config directory (see Platforms).

Whitespace around the token is trimmed. An empty variable counts as unset.

A named-but-missing token file is an error, not a fall-through. If VENUE_TOKEN_FILE is set and the file is missing, empty or unreadable, the Kit does not go on to try <config>/venue-token. It reports the problem (step 3 above). A typo in the variable shows up as an error instead of being hidden by another token source. VENUE_TOKEN still wins over a broken VENUE_TOKEN_FILE. The default file (item 3 of the lookup) is different: if it is missing or empty, that just means “not configured”.

Dart and Rust implement this the same way, with tests in both. In Rust a token that is found cannot connect to anything: with auto the session is local and its description says the crate has no remote Venue session, and with on the context fails to open.

The health check waits up to 2 seconds for an answer. Opening a connection to an unreachable address is capped at 5 seconds by the Dart transport, so it can delay startup. In auto mode that delay is followed by the local fallback.

The token belongs to one consumer name. Use the token issued for the name in venue.consumer. A token used under another name is refused by the daemon with HTTP 403 (forbidden, see Refusals); this was seen with a real daemon.

with_hold is the same without the options and returns only the body’s value. with_hold_opts also hands back the hold, so you can read after the call whether any renewal failed.

What withHold does

  1. hold. If Venue refuses, the body never runs and nothing is released.
  2. start. If that fails, the hold is released and the start error is what you see.
  3. Renews every third of the lease (clamped to between 1 second and 1 hour), unless you pass renewEvery. Renewals never overlap, and none is sent after release.
  4. Runs your body.
  5. Releases, whether the body returned, threw, or (in Rust) panicked.

Two things are recorded, not thrown:

  • A failed renewal sets hold.leaseLost (Rust: lease_lost()), counts in renewalFailures, and calls onLeaseLost once, on the first failure. The body keeps running. Stopping the work is your decision. leaseLost is latched by a single failed renewal, so one network blip sets it even if most of the lease is still left. Renewing does not update hold.expiresAt, so the hold object cannot tell you how much lease remains.
  • A failed release never replaces your body’s result or error. It is kept in hold.releaseError.

The render-queue demo treats a lost lease as a failed job: it cancels the work, shows the reason, and offers Retry, because after a failed renewal the app cannot be sure Venue still counts the slot as its own. That is a policy choice for one app, not something the Kit does for you. It is tested with a session whose renewals fail. A daemon that stops answering mid-job was not tested.

The context does not release holds taken with hold() directly. ctx.close() closes the session and nothing else. Only withHold and withHoldWaiting release what they took. If you call hold() yourself, release it yourself.

Wait for room

withHoldWaiting retries a refused hold until it is granted or maxWait is used up.

import 'dart:async';
import 'package:app_context_kit/app_context_kit.dart';

Future<void> main() async {
  final manifest = AppManifest.fromJson({
    'id': 'com.slashbuilder.demo.render-queue', 'name': 'Render Queue', 'version': '0.1.0',
  });
  // Run with APP_CONTEXT_MODE=mock: the fake node has room for one hold at a time, so the second job has to wait.
  final ctx = await AppContext.open(manifest, fakeCapacity: 1);
  final venue = ctx.venue;

  final first = await venue.hold(const VenueNeed(name: 'first', contractClass: 'container.run.v1'));
  Timer(const Duration(seconds: 2), () => venue.release(first));

  try {
    final answer = await venue.withHoldWaiting(
      const VenueNeed(name: 'second', contractClass: 'container.run.v1'),
      (hold) async => 'got ${hold.name}',
      maxWait: const Duration(seconds: 10),
      retryEvery: const Duration(seconds: 1),
      onWaiting: (refusal, attempt) => print('refused (${refusal.kind.name}), attempt $attempt: ${refusal.plainReason}'),
      onLeaseLost: (hold, error) => print('lease lost on ${hold.name}: $error'),
    );
    print(answer);
  } on VenueRefused catch (e) {
    print('gave up: ${e.kind.name}${e.retryable ? " (could have been retried)" : ""}: ${e.plainReason}');
  } on VenueUnavailable catch (e) {
    print('Venue could not be asked: ${e.reason}');
  } on HoldWaitCancelled {
    print('cancelled');
  } finally {
    await ctx.close();
  }
}

Rules:

  • maxWait is required. Duration.zero makes it exactly withHold (fail fast).
  • It retries doesNotFit always. It retries forbidden only while holds() shows this consumer still holds something. See the next section for why, and for when that is wrong.
  • It never retries VenueUnavailable, and never retries an error thrown by your body.
  • Waiting is counted in naps of retryEvery, not read from a clock, so it behaves under a test’s fake time. It naps at most maxWait ~/ retryEvery times and then rethrows the last refusal.
  • cancel (a Future) ends the wait at once with HoldWaitCancelled. A hold granted in that same instant is released, not leaked.
  • retryEvery must be positive.

Every waiting consumer polls Venue about once per retryEvery. Venue has no queue and no push, so there is no way to be told “there is room now”. In one earlier test with five waiting jobs against a real daemon, each job asked 15 to 20 times.

Rust has no with_hold_waiting. The refusal kinds are enough to write the loop yourself (see below), but the Kit does not ship it.

Handling them

Rust, telling the three apart:

#![allow(unused)]
fn main() {
match ctx.venue.hold(&need, 30) {
    Ok(h) => ctx.venue.release(h)?,
    Err(e) => match e.refusal_kind() {
        Some(RefusalKind::DoesNotFit) => println!("full right now, retry later: {e}"),
        Some(RefusalKind::Forbidden) => println!("not allowed, do not retry: {e}"),
        None => println!("Venue could not be asked: {e}"),
    },
}
}

With the fake session at capacity this prints full right now, retry later: Venue refused (doesNotFit): the fake node is full.

The documented limitation: one code for the limit and for everything else

Venue answers its per-consumer live-hold limit with HTTP 403 and the code forbidden. It gives the same code for a missing grant, an observer token, and a token that does not match the consumer. There is no machine-readable reason, so the Kit cannot tell “you are over your own limit” (will clear when you release something) from “you may never do this” (will not).

The Kit’s current rule: forbidden is not retryable. withHoldWaiting adds a heuristic: if the daemon says forbidden and holds() shows this consumer still has live holds of its own, assume it is the limit and wait. If you have none, give up at once.

The heuristic is wrong in one case. A consumer that both holds something and lacks the grant for a new kind of work will wait the full maxWait for nothing and then get the real refusal. Checking costs one extra GET /v1/holds per retry. Verified against a real daemon: a consumer at its limit waits, is granted when one of its own holds ends, and gives up at maxWait with forbidden when nothing is released. The case where the heuristic is wrong was reasoned from the code, not run.

The fix belongs to Venue: a distinct reason, or status, for “over the live-hold limit”. The Kit would then drop the heuristic. See Open items.

Leases, crashes and orphan holds

A hold is a lease. Venue frees it when the lease runs out unless you renew it. That is what gives a dead app’s reservation back, and it is also why a crash costs you something.

What happens to a killed app’s holds. They stay live, and keep counting against the consumer’s limit, until the lease lapses. A clean exit releases them; kill -9 does not.

Measured against a real throwaway daemon, three running holds with a 6 second lease, the process killed with kill -9, then the app relaunched at once:

This runEarlier run
Orphans reported by the startup scan3, at 0.24 s after the kill, each with 4.4 s left3, at 0.23 s, each with about 4.0 s left
New job granted5.4 s after the kill4.3 s after the kill
Holds left at the daemon afterwards00

The spread is arithmetic. The app renews every third of the lease (2 s here), so the last renewal happened up to 2 s before the kill and the lease ends 4 to 6 s after it. The relaunched job then polled once a second, so it was granted at the next poll after the lapse.

With the Kit’s default lease of 300 seconds, the same crash keeps the consumer’s quota for up to five minutes. The render-queue demo’s 30 second lease (renewed every 10 s) would cost up to about 30 s.

So keep leases short. Choose the shortest lease that still survives your renewal being late by a couple of intervals. Tradeoff: a shorter lease means more renewal traffic and a smaller margin for a slow network or a stalled event loop. Do not take the default 300 seconds for work that lasts seconds.

A clean quit of the render-queue demo with three jobs running left no holds within 1.5 seconds. That works because the app’s close hook cancels its jobs and waits for each withHold to release. This was measured earlier and not re-run for this guide.

A second liveness clock

The roster (the presence file each app writes) and the Venue lease both answer “is this process still alive?”, with separate timers. After kill -9 they disagreed in an earlier measurement: Venue freed the hold in 6 s, the roster still said “running, stale” for up to 15 s. The Kit has not merged them. Treat the Venue lease as the answer for Venue, and the roster as the answer for “who is on this machine”.

Pinned TLS

By default the daemon is plain HTTP on the loopback interface. The bearer token travels in a header, in the clear. That is acceptable on 127.0.0.1. For any daemon on another machine, use HTTPS.

A self-signed daemon (venued --tls) prints its certificate fingerprint when it starts. Give the app that value:

VENUE_DAEMON=https://127.0.0.1:17879 \
VENUE_DAEMON_FINGERPRINT=sha256:<the 64 hex digits venued printed> \
VENUE_TOKEN_FILE=/path/to/token \
  dart run bin/hold.dart

How the pin works:

  • With a fingerprint, no certificate authority is trusted at all. Every certificate is shown to a check, and only one whose SHA-256 equals the pin is accepted. There is no hostname check and no expiry check. The pin is the identity.
  • Nothing is sent, not even the token, to a server that does not present the pinned certificate.
  • These spellings are accepted: with or without sha256:, upper or lower case, with or without colons. They are normalised to sha256: and 64 lower-case hex digits. (Covered by dart/app_context_kit/test/transport_pin_test.dart; the Rust crate has no TLS client.)
  • Without a fingerprint, Dart falls back to the system’s trusted roots, so a CA-signed daemon should work (not tested).

What a wrong pin looks like depends on how you reach the daemon.

Through AppContext.open, the health check fails first, and the context reports only that the daemon did not answer. In auto mode:

Venue: local (Venue did not answer at https://127.0.0.1:17879)

The note has severity warning. In on mode, open fails with “Venue is required but https://127.0.0.1:17879 did not answer”. This is the same text whether the pin is wrong, missing or malformed. The reason is not in the text.

Through a session you build yourself (RemoteVenue with IoTransport(fingerprint: ...)), the reason is in the error. These are the three VenueUnavailable messages from a real TLS daemon:

GET /v1/nodes: the daemon's certificate (sha256:0aded5...5974) is not the one that was pinned (sha256:abab...abab)
GET /v1/nodes: the daemon's certificate is not trusted by the system; a self-signed venued needs its fingerprint (VENUE_DAEMON_FINGERPRINT=sha256:...)
GET /v1/nodes: the fingerprint "nonsense" is not 32 bytes of hex (sha256:...)

(The first line has the fingerprints shortened here.) If an app shows “did not answer” and you expect TLS, build a RemoteVenue by hand as above to see the cause.

Plain http:// pointed at a TLS port fails quickly rather than hanging (well under 10 s in Dart).

Registering an app with Venue

Venue only grants holds to consumers it knows about, and only for the kinds of work they have been granted. Today, introducing an app to a daemon takes four manual steps. These are the four a throwaway registry needed for each demo app, written as the Venue project’s own command line (that command line is not part of the App Context Kit repository):

  1. Add an entry for the consumer to the registry’s authority.yaml, with a class, a priority cap and a live-hold limit: - {name: render-queue, class: Consumer, maxPriority: 100, maxLiveHolds: 3}
  2. venue --as declared principal add render-queue
  3. venue --as declared grant use container.run.v1 --principal render-queue
  4. venue --as declared token add render-queue --manager render-queue, which prints the token.

Steps 2 and 3 need an operator with authority over the registry; the commands pass --as declared on steps 2 to 4; what that flag does is described in Venue’s own documentation. Grants are authority: they decide what a program may ask the machine to do.

The Kit cannot do this for the app, and should not. An app that could grant itself the right to run work would make the limit meaningless. So “Venue wired in from the first launch” cannot be done by the app on its own. The app can only ship its manifest and wait for someone with authority to provision it.

What a provisioning step would need (none of this is built; it is a description of the gap):

  • Input. The manifest’s venue block gives the consumer name. It does not say which contract classes the app will ask for. Today that is in the app’s code (container.run.v1 above). The manifest could declare it, so the provisioner can build the grants. The Kit does not.
  • Decisions only an operator can make. The priority cap and the live-hold limit (3 in the demo registry).
  • Authority. Something that holds the right to edit the registry and run steps 2 to 4: an installer, an app store, or a person. Which of these runs it is undecided.
  • Delivery. The token has to reach the app: a file at <config>/venue-token, or an environment variable set by whatever launches it. Under the macOS sandbox, a token file outside the app’s container cannot be read; see Platforms.
  • Repeatability. Running it twice on upgrade should not fail or duplicate, and uninstalling should remove the grant. Not designed.

Running without Venue

Venue is optional. An app can run entirely local:

  • Set "venue": { "mode": "off" } and nothing ever connects. The session is local with the description “Venue is off for this app”.
  • Leave the mode at auto and configure nothing. The session is local (“Venue not configured”). If a daemon is configured later, the same binary connects.

What local does:

  • Holds exist only in your process. A second hold with the same name in the same process is refused with doesNotFit. Different names are all granted, with no limit. In an earlier test, five render jobs ran at once under local, where a real daemon with a limit of 3 would have run three.
  • renew does nothing, nodes() is empty, and holds() lists this process’s holds.
  • Nothing protects against another app, or another copy of yours, using the same resource at the same time.

If your app can wait for capacity, the people using it get the right behaviour only on a venue session. On local, say so (the description already does).

Coordination guide: copies of one app talking to each other

Reference page pulled from app-context-kit at commit 4797e81. Edit it in the Kit, not here.

This guide is for a developer who wants two running copies of the same app to find each other, agree on who is there, and exchange messages. It covers the peer layer of the App Context Kit: what the Kit does, what you write, how to start it, and what it does not do.

Status, so you know what you are reading. The peer layer is implemented in the Dart core (dart/app_context_kit/lib/src/peers/). Two providers are built: an in-memory fake network (tests and mock mode) and a loopback provider (copies on one machine). No provider for a real network exists yet, and the Rust implementation has no peer code. Every example in this guide that has a file under examples/coordination/ runs as a test; the commands are in Run the examples.

1. The model

The Kit finds, authenticates, connects and routes. Your app supplies a hook and decides what the messages mean. The Kit never reads the payload.

The Kit doesYour app does

“Never reads the payload” is literal. A message carries a kind string and a schema integer that you choose, and an opaque byte payload. The Kit routes on its own header (see the envelope) and hands you the bytes.

You get one hub per channel. A hub is one PeerHub object that owns the links to every other copy of your app. An app with several unrelated conversations either starts one hub per conversation or writes one hook that routes by kind prefix (a sample is MuxHook in sample_hooks.dart).

2. The scope key

Two copies are peers only if they have the same account and the same app id. Anything else is never offered to your hook and never admitted.

PartWhere it comes from
App idid in app.json (the manifest)
AccountAPP_CONTEXT_ACCOUNT, else account in the app’s config.json, else local
DeviceAPP_CONTEXT_DEVICE, else device in config.json; if neither exists the Kit generates d- plus 8 hex digits and saves it
Instance8 random hex digits, drawn each time the app opens (ctx.instance)

A peer is identified by (device, instance), the PeerId. Two copies on one device are two peers. local is the account of a machine that has no household account; it is a placeholder until something issues a real one.

Scope is checked in three places, so a bug in one does not open the others:

  • The provider does not list candidates from another scope and refuses to dial or accept one. The loopback provider also keeps one directory per account and app, so it never reads another scope’s files.
  • The hub drops a candidate or an incoming link whose claimed scope differs from its own, and counts it in hub.stats.scopeViolations.
  • Every frame carries account and app in its header. A frame with a different scope cuts the link.

ping_test.dart checks this: a copy of the app, a copy with another app id and a copy with another account share one network, and none of the three sees any peer.

Scope is a name, not a credential. The default authenticator (OpenAuthenticator) accepts every peer in scope, and no per-app credential exists yet. Treat the scope key as a way to keep copies of different apps and accounts apart, not as access control. The authenticator is the seam where a real check goes; see per-app credentials. A security review is pending; details withheld.

Identifier rules for the loopback provider: account, app, device and instance become directory and file names, so they may contain only letters, digits, ., _ and -, may not start with ., and may be at most 128 characters. Anything else makes the hub fail to open, which ctx.startPeers reports in handle.error.

3. The hook: five jobs

A hook is a subclass of AppCoordination (coordination.dart). It has five jobs and one convenience:

#MemberWhen the Kit calls itWhat you return or do
1String get channelOnce, when the hub is builtThe conversation this hook owns, such as "default" or "game". A peer on another channel is rejected at the handshake
2Object? hello()Each time a link opensAnything JSON-encodable, or null. Describe your current state (a version, a digest, a protocol number). The Kit carries it and never reads it
3FutureOr<Admit> admit(Peer, Object? theirHello)After the Kit has checked identity, once per linkAdmit.accept(), Admit.acceptReadOnly() or Admit.reject(reason). May be async; the link waits
4void onPeer(Peer, PeerChange)A peer is found, ready or lostReact. Runs before the same event appears on hub.changes
5void onMessage(Peer from, AppMessage)A message arrives from a ready peerYour meaning lives here. It is synchronous: queue async work yourself
void attach(PeerHub)Once, from hub.start()Keep the hub so you can call send, broadcast, request and reply. The default does nothing

acceptReadOnly only sets peer.readOnly. The Kit does not filter anything for a read-only peer, and the other side is not told. You decide what read-only means, for example by ignoring that peer’s write messages in onMessage.

A hook must not throw. If it does, the hub catches the error, counts it in hub.stats.hookErrors, passes it to PeerHubOptions.onHookError if you set one, and carries on.

A complete hook: “ping”

This is the whole of a working app’s coordination code. Any copy can ping another, and the other answers with its device name. It is examples/coordination/lib/ping_hook.dart, unchanged.

import 'dart:async';

import 'package:app_context_kit/app_context_kit.dart';

/// A complete coordination hook: the five jobs, and nothing else.
///
/// "ping": any copy can ask another copy "are you there?", and the other copy answers with its device name.
class PingHook extends AppCoordination {
  PeerHub? hub;

  /// Peer changes as the Kit reported them, e.g. "ready desktop".
  final List<String> events = [];

  /// Messages this hook did not understand. A hook counts these instead of throwing.
  int ignored = 0;

  // 1. Which conversation inside the app this hook owns.
  @override
  String get channel => 'ping';

  // The Kit hands the hook its hub once, from PeerHub.start().
  @override
  void attach(PeerHub hub) => this.hub = hub;

  // 2. What to tell a peer when a link opens. Any JSON-encodable value.
  @override
  Object? hello() => {'proto': 1};

  // 3. Whether to talk to this peer, given what it said in its hello.
  @override
  FutureOr<Admit> admit(Peer peer, Object? theirHello) =>
      theirHello is Map && theirHello['proto'] == 1
          ? const Admit.accept()
          : const Admit.reject('ping protocol 1 only');

  // 4. A peer was found, became ready, or was lost.
  @override
  void onPeer(Peer peer, PeerChange change) =>
      events.add('${change.name} ${peer.id.device}');

  // 5. The app's meaning lives here. Answer a ping; count anything else.
  @override
  void onMessage(Peer from, AppMessage message) {
    if (message.kind == 'ping' && message.schema == 1 && message.requestId != null) {
      PeerJson.quiet(hub!.reply(message, PeerJson.encode({'pong': hub!.device}), schema: 1));
    } else {
      ignored++;
    }
  }

  /// Ask [peer] if it is there. Returns the name it answered with, or null for an answer in the wrong shape.
  /// Throws a PeerError (PeerTimeout, PeerLost, ...) if there is no answer.
  Future<String?> ping(Peer peer) async {
    final reply = await hub!.request(peer, PeerJson.encode({'n': 1}), kind: 'ping', schema: 1);
    final body = reply.jsonBody;
    return body is Map && body['pong'] is String ? body['pong'] as String : null;
  }
}

Peers and their states

A Peer is read-only to you. Its state is one of found, connecting, ready, rejected or lost. found means the provider announced it; connecting means a link is being opened or the handshake is running; ready means both sides admitted each other. peer.hello is the decoded hello once received, and peer.rejectReason and peer.lostReason say why a peer ended (goodbye, link closed, hub closed, withdrawn, and others).

A Peer object is never reused. A copy that goes away and comes back is a new Peer with the same PeerId. Keep the PeerId if you need to find the peer again; calling send with a Peer that has been replaced throws PeerNotAvailable. A rejected peer is not redialed until the provider withdraws it and announces it again.

A rejection shows up as a lost event on both sides, with peer.state == rejected. hub_behaviour_test.dart checks it: one side’s admit rejects with "proto 2 only", and the other side’s peer ends with rejectReason == 'rejected by peer: proto 2 only'.

6. Providers

The hub talks to two small interfaces, PeerProvider and PeerLink (provider.dart), so the same hook runs over any provider. A provider announces this copy, reports other copies in the same scope (discover()), dials one (connect), and hands over links that others dialed (incoming). A link is one ordered, message-framed connection: one send arrives as one inbound event.

Fake network: tests and mock mode

FakePeerNetwork (fake_network.dart) is an in-memory network. Several hubs join one network, each through its own provider. It enforces the scope key itself and lets a test change the world while it runs:

Loopback: copies on one machine

LoopbackProvider (loopback_provider.dart) connects copies that run on one machine, as processes. It needs nothing but a shared directory.

Announcement files. Each copy listens on a TCP port on 127.0.0.1 (never a routable address; the operating system picks the port) and writes one file:

<peers dir>/<account>/<app id>/<device>@<instance>.json

with these fields. This file was written by a run of the stopwatch probe; loopback_test.dart asserts the key set and the path.

{"account":"local","app":"com.slashbuilder.demo.stopwatch","device":"desktop","instance":"48e784da","port":52367,"pid":63779,"beat":1792850562108}

beat is a wall-clock time in epoch milliseconds. The file is written to a temporary name and renamed, so a reader never sees half a file.

Finding each other. Each provider reads the directory for its own account and app every 100 ms (pollInterval). A file naming another scope than its directory is ignored. A candidate is offered if its file is under 4 KiB, parses, has a valid port, and has a recent beat.

Connecting. Only the copy with the lower PeerId dials, so two copies never open two links. A frame on the wire is a 4-byte big-endian length followed by the envelope bytes. The dialer’s first frame is a preface naming who it claims to be; the accepting side closes the socket if the preface names another scope or is garbage, before the hub sees a link. A dial that fails is retried after 0.2 s, doubling to a 5 s ceiling, at most 10 attempts; after that the hub waits for the provider to announce the copy again.

Beat, staleness and reaping. This is how a crashed copy disappears.

SettingDefaultMeaning
announceEvery1 sEach provider rewrites its own file with a fresh beat
staleAfter4 sA file whose last beat is older is not offered, and a peer already known from it is withdrawn
reapAfter60 sA file whose last beat is older is deleted by whichever copy notices. A paused copy rewrites its file at its next beat

A file with no beat (one made by hand) is aged by its modification time. The provider does not check whether the pid in the file is alive: a pid means nothing across pid namespaces, can be reused, and Dart has no portable check that does not spawn a process. The cost of the beat is one small write per second per process.

What a crash looks like. On a clean close() the copy sends kit.bye, deletes its file, and the other copy sees lost with reason goodbye; it is not redialed. If the process is killed, the operating system closes its sockets, so the survivor sees the link drop at once. But the file is still there and still has a recent beat, so the dead copy is still announced and the survivor sees it as found again. It stays that way until the beat is older than staleAfter. One death is therefore three events: lost, found, lost.

Measured today on macOS (Apple silicon) by dart test test/peers/two_process_test.dart -r expanded in dart/app_context_kit, which starts real operating-system processes over one temporary directory and kills one with SIGKILL. Two runs, one for each side of the dial rule:

The found after the first lost is a known rough edge: the hub cannot yet tell “link dropped” from “gone” earlier than the beat allows. Tuning. ctx.startPeers and ctx.peerHub take PeerHubOptions but not the loopback timings. To change staleAfter or announceEvery, build the provider yourself and pass it: ctx.peerHub(hook, provider: LoopbackProvider(directory: ..., staleAfter: ...)).

Limits.

  • One machine, one user. The loopback provider has no encryption and no authentication. Use it for same-user coordination on one machine and for tests, not across users or trust boundaries.
  • On macOS, a sandboxed app has its own container. The peers directory (and the roster) must be reachable by every copy: the default location is inside the container and works for copies of one app; a path outside the container leaves the app working alone. The sandbox entitlements com.apple.security.network.client and com.apple.security.network.server are both needed to dial and to listen. Flutter’s macOS template grants only network.server in Debug and neither in Release; the notepad and minesweeper projects add both. With only server, the recorded observation was that two sandboxed copies listen but never connect, with nothing in the log. PLATFORMS.md has the full table; the observation was not re-run for this guide.
  • Environment variables you set in a shell reach an app you start from that shell. They do not reach one started from Finder or the Dock.

7. The envelope

Every frame between two copies is one envelope: a header the Kit reads and a payload it does not (envelope.dart). The wire form is UTF-8 JSON with the keys in a fixed order:

{"v":1,"account":"a","app":"dev.x","channel":"default","from":{"device":"d","instance":"i"},
 "seq":1,"kind":"msg","schema":0,"rid":7,"payload":"<base64>"}
FieldMeaningLimits
vEnvelope version. A different value is rejected1
account, appThe scope key1 to 256 characters, no control characters
channelThe hook’s channelsame
from.device, from.instanceThe sender’s PeerIdsame

kindMessage type. Yours, or a reserved kit. kind1 to 256 characters

Unknown extra keys are ignored, so a later version can add fields.

The outer cap is 1 MiB. A payload over 1,048,576 bytes is an EnvelopeError on send. The largest frame the decoder will look at is 1,406,296 bytes (the base64 of a full payload plus 8,192 bytes of header room). That is the Kit’s limit. A provider may carry less; see real transports.

Reserved kinds. Kinds that start with kit. belong to the Kit, and your app cannot send them (ArgumentError). The Kit uses these:

KindPurpose
kit.helloFirst frame each way: a nonce and your hello()
kit.authThe authenticator’s proof over the other side’s nonce
kit.ready“I admitted you”
kit.reject“I refuse you”, with a reason of at most 256 characters
kit.byeGraceful close; the peer is not redialed
kit.replyThe answer to a request

An unknown kit. kind from a peer is ignored. kit.reply is consumed by the hub and completes the request future; it never reaches onMessage.

Request and reply. request gives the outgoing frame an rid from a per-hub counter that starts at 1. The other side’s onMessage sees it as AppMessage.requestId; hub.reply(message, payload) sends a kit.reply with the same rid. The hub matches replies to waiting requests by (peer, rid), so the Kit’s correlation does not depend on a transport’s own message ids. A reply that is late or unknown is ignored. A request that times out cancels its frame if the frame has not been written yet.

8. Ordering and loss

seq numbers the frames in one direction of one link. It starts at 1 on every new link, so a reconnect restarts it. It counts the Kit’s own frames too. kit.hello, kit.auth and kit.ready take 1, 2 and 3, so the first message your app receives from a peer has seq 4. A kit.reply or kit.bye takes a number as well.

The hub delivers each peer’s frames to you in seq order, once:

  • A frame that arrives early waits in a reorder buffer of 16 frames.
  • A gap that is not filled within 500 ms, or a buffer that overflows, is skipped. The hub counts it in hub.stats.gapsSkipped and delivers what it has.
  • A frame at or below the last delivered seq is a duplicate or a late arrival after a skip, and is dropped (duplicatesDropped).
  • A peer that floods more than 256 undelivered frames on one link has the link dropped.

You see loss as a jump in AppMessage.seq. hub_behaviour_test.dart drops the second of three messages on the fake network. The receiver gets two:

expect(seqs, [4, 6]);

A jump says that one or more frames from that peer were skipped. It cannot say which: the lost frame might have been a reply. If you need to detect a lost message precisely, put your own counter or version in the payload.

Ordering is per sender. The Kit gives you no order between messages from two different peers.

9. Delivery

Delivery is best effort.

  • send completes when the transport took the frame, not when the peer received or applied it. hub_behaviour_test.dart sets the fake network to drop every frame and shows that send still completes without error.
  • If the link ends before a queued frame is written, the send future fails with PeerLost. Queued messages are dropped when the peer is lost.
  • There is no retry and no replay. A message sent before a peer exists is not kept for it: a broadcast with nobody ready returns an empty sent list, and a copy that arrives later never sees it.
  • send to a peer that is found or connecting is queued and written once the peer is ready. App frames from a peer are not delivered to you before it is ready.
  • request/reply is the one acknowledgement the Kit has: a reply proves the other hook ran. A request that gets no reply fails with PeerTimeout (the other hook may still have run).

If you need “it was applied”, build it from a reply. The minesweeper and notepad apps did; the stopwatch accepted a possible duplicate instead. See the patterns.

10. Backpressure

Each peer has an outgoing queue of messages not yet handed to the transport. It holds at most 256 messages or 8 MiB of payload (PeerHubOptions.outboxMessages, outboxBytes). When it is full, send, request and reply fail with PeerOutboxFull on the returned future, and broadcast reports that peer in failed. The Kit does not drop an older message to make room, because only your app knows what is safe to drop.

What to do depends on the message. For state (“the current note”, “the timer”), send the newest value and let PeerOutboxFull mean “skip this one; the next change carries the state anyway”. For events that all matter, await each send before the next. hub_behaviour_test.dart sets outboxMessages: 2, sends ten messages without awaiting, and counts the PeerOutboxFull failures.

13. Three worked patterns

The three demo apps that use peers (stopwatch, notepad and minesweeper, in The Kit Book) each used the hook for a different kind of meaning. The snippets below are copied from their code.

A signal: “the timer finished” (stopwatch)

The stopwatch app shares one countdown between copies. This pattern is only the announcement: when the countdown ends, exactly one copy should say so, and the others should show “finished on laptop #3fa2” instead of announcing it again.

Which copy announces is the app’s decision, not the Kit’s. Every start, pause or reset bumps a stamp, a pair of a revision number and the id of the copy that made the change (its “writer”). The rule: the writer of the current stamp announces. If the writer is no longer among hub.readyPeers, the lowest-numbered live copy announces. Any other copy waits for the timer.finished message and, if it has not arrived after a 2-second grace, announces itself. The announcement is a broadcast with a kind and schema the app chose. A late joiner is not told what it missed; the countdown state rides in its hello() instead (see the replay entry in section 14).

Delivery is best effort, so the announcement can be lost. The app does not try to prevent that with an acknowledgement; it prevents silence instead. Under a partition two copies may both announce. The app chose “at least once” on purpose, and the comment at the top of the file says so. It accepts a possible duplicate announcement rather than a possible missing one.

The Kit contributes the list of ready peers (hub.readyPeers, used to decide who is alive), the broadcast, and the guarantee that one peer’s messages arrive in order. The stopwatch also replicates the countdown itself with a last-writer-wins stamp; that is a second use of the same hook, and this section covers only the signal. From the stopwatch demo app’s lib/coordination/shared_timer.dart:

/// This copy's countdown ran out. Announce if we are the announcer, else wait for the announcer.
void countdownEnded(CountdownModel done) {
  if (_told == stamp) return;
  if (_isAnnouncer()) return _announce(done);
  final at = stamp;
  _grace = Timer(takeoverGrace, () {
    if (_told != at && stamp == at) _announce(done);
  });
}

bool _isAnnouncer() {
  final h = hub;
  if (h == null || stamp.rev == 0 || stamp.writer == _me) return true;
  final ready = h.readyPeers;
  if (ready.any((p) => p.id.toString() == stamp.writer)) return false; // the owner is alive: it announces
  return ready.every((p) => h.id.compareTo(p.id) < 0); // owner gone: the lowest live copy does
}

void _announce(CountdownModel done) {
  _told = stamp;
  final label = formatMs(done.durationMs, tenths: false);
  onFinished(Finished(label: label, by: hub?.id ?? const PeerId('local', 'local'), local: true));
  final h = hub;
  if (h != null) {
    final ended = _stateJson(done)..['label'] = label;
    PeerJson.quiet(h.broadcast(PeerJson.encode(ended), kind: 'timer.finished', schema: 1));
  }
}

A sync with an app-defined conflict rule (notepad)

The notepad app keeps the same notes on every copy. The Kit carries bytes between copies; it has no store, no merge and no idea what a note is. The hook file is 29 lines and forwards each of the five jobs to a sync engine, about 500 lines in note_sync.dart, which is the app’s own.

The central choice is what happens when two copies edit the same note while apart. The engine tracks a version vector per note, so it can tell “you are behind” from “we both edited”. A timestamp cannot tell those apart: it always orders two edits, and one edit silently loses. When the versions are concurrent, the engine keeps both: the version that sorts later (by updatedAt, then device, then a content hash) keeps the note’s title and place, and the other becomes a new note titled <title> (conflict from <device>). The rule is symmetric and total, so both copies reach the same decision without talking, and they derive the same id for the new note, so they converge instead of duplicating. The person is told what happened. Edit beats delete: a delete never destroys a concurrent edit. Identical text on both sides is not a conflict.

Content moves by pull. Small sync.have messages say “note X is at version V”. A copy that is behind asks with request, one part at a time, because request/reply is the only acknowledgement the Kit has. A late joiner puts only a digest in its hello(); if the digests differ, each side sends its index and the one that is behind pulls.

None of this is in the Kit, by design: the Kit does not interpret payloads. The hook is the right shape for meaning; it is not a sync framework. From the notepad demo app’s lib/coordination/note_sync.dart:

void _applyRemote(Note remote, Vv rvv, String rby) {
  final id = remote.id;
  if (host.isDamaged(id)) return;
  host.flushNote(id);
  final local = meta[id];
  final order = local == null ? VvOrder.before : local.vv.compare(rvv);
  try {
    switch (order) {
      case VvOrder.equal || VvOrder.after:
        return;
      case VvOrder.before:
        _put(remote, rvv, rby);
      case VvOrder.concurrent:
        final mine = host.note(id);
        if (local!.deleted || mine == null) {
          _put(remote, local.vv.join(rvv), rby); // edit beats delete
        } else if (hashNote(mine) == hashNote(remote)) {
          meta[id] = Meta(local.vv.join(rvv), by: local.by, hash: local.hash); // same text on both: only the histories merge
          _save();
          _announce([id]);
        } else {
          _conflict(mine, local, remote, rvv, rby);
        }
    }
  } on FileSystemException catch (e) {
    report('Could not store a synced note: ${e.message}. It will be tried again at the next sync.');
  }
}

/// Does A sort after B? Symmetric and total, so both copies pick the same winner with no conversation.
bool _beats(Note a, String aBy, Note b, String bBy) {
  final t = a.updatedAt.compareTo(b.updatedAt);
  if (t != 0) return t > 0;
  final d = aBy.compareTo(bBy);
  return d != 0 ? d > 0 : hashNote(a).compareTo(hashNote(b)) > 0;
}

A handoff with confirmation (minesweeper)

The minesweeper app can hand a game to another copy. “Give the game away” changes state on two sides, and the Kit has no transaction, so the app builds the handoff from request/reply:

  1. The sender offers (game.offer: difficulty, status, seconds, squares open; no board).
  2. The receiving person says yes or no. An offer never changes a board by itself.
  3. The receiver requests the board (game.take). The reply is the data. The sender serves it only for an offer it made, to the peer it made it to.
  4. The receiver applies the board. Minesweeper.fromJson is strict: anything inconsistent is refused and nothing changes.
  5. The receiver requests game.taken. Only when that request arrives does the sender release its game.

If the confirmation is lost, both copies keep the game: a duplicate, never zero. The receiver is told “did not confirm”. The app accepts one known hole, and says so in its source: moves made on the sender between serving the board and hearing game.taken are lost to the receiver. Closing it needs a lock on UI state that the hook cannot own.

The same offer also starts “play together”, where each move is sent as a small absolute message plus a checksum of the sender’s board, and a receiver whose checksum differs pulls the whole board. Two players who make the first move at the same instant are resolved by an epoch, then the lower PeerId. All of that is the app’s. The Kit supplied request/reply, the ordered delivery per sender, and admit, which the hook uses to refuse a peer with another protocol number. From the minesweeper demo app’s lib/coordination/game_hook.dart:

/// The person said yes to [o]: pull the board, apply it, confirm. Returns what happened, in words.
Future<String> accept(Offer o) async {
  final h = hub!;
  final peer = h.readyPeers.where((p) => p.id == o.from).firstOrNull;
  incoming.remove(o.from);
  if (peer == null) return _done('${PeerJson.label(o.from)} is no longer connected.');
  try {
    final reply = await h.request(peer, PeerJson.encode({'offer': o.id}), kind: 'game.take', schema: 1);
    final j = reply.jsonBody;
    if (j is! Map || j['ok'] != true || j['board'] is! Map) return _done('${PeerJson.label(o.from)} no longer has that game to give.');
    try {
      host.adoptBoard((j['board'] as Map).cast<String, Object?>());
    } on FormatException catch (e) {
      return _done('The game from ${PeerJson.label(o.from)} was not accepted: ${e.message}');
    }
    if (o.mode == 'share') sharing = o.from;
    try {
      final ack = (await h.request(peer, PeerJson.encode({'offer': o.id}), kind: 'game.taken', schema: 1)).jsonBody;
      if (ack is Map && ack['ok'] == true) return _done(o.mode == 'share' ? 'Playing together with ${PeerJson.label(o.from)}.' : 'Took over the game from ${PeerJson.label(o.from)}.');
    } on PeerError {
      // fall through
    }
    return _done('Took the game, but ${PeerJson.label(o.from)} did not confirm: it may still show the game too.');
  } on PeerError catch (e) {
    return _done('Could not get the game from ${PeerJson.label(o.from)}: ${e.message}');
  }
}

Smaller gaps you will meet:

  • onMessage is synchronous. The hub processes one link’s frames one at a time. If a message needs async work, queue it in your hook (notepad has a pump with a bound).
  • One hub is one channel, and admit is one answer per peer. “Accept this peer but not its offers” cannot be expressed. Use one hub per facet or a mux hook.
  • No “same device” signal. Two copies with one device id are one replica to your files. Notepad compares peer.id.device itself in admit and rejects them.
  • No place for hook state, and no clock. A stamp or a version that must survive a restart goes in your own file. A timer inside a hook is a plain Timer.
  • hello() is a snapshot taken at connect. A command can land between the hello and ready; the stopwatch re-checks on ready for that reason.

15. Real transports

Only the fake network and the loopback provider are built. There is no provider for a real network, and no Hearth provider for the Dart hub. What follows is what a provider has to do, and what was learned about Hearth before writing one.

What every provider must do

The contract is in provider.dart. In short:

  • open(self) announces this copy and starts accepting. discover() replays what is known, then follows changes, and re-emits a candidate with available: false when it goes away. connect(candidate) throws PeerScopeError outside the scope and PeerConnectError when it cannot reach the candidate. incoming buffers until listened to. close() is idempotent.
  • Never offer, dial or accept another account or app id. The hub checks too, but a provider that leaks scope is a bug.
  • Discovery must be symmetric. Only the lower PeerId dials, so both copies have to see each other, or neither connects.
  • A link delivers one send as one inbound event. Framing is the provider’s job. send completes when the transport has taken the bytes.
  • A link’s remote identity is a claim. The hub checks it against the frame headers and the authenticator’s proof and drops the link if the scope differs. Only a real authenticator makes the proof mean anything.

What Hearth would add

These come from the spec and from tests against a local Hearth hub. They are requirements for a provider, not code that exists in the Dart hub.

  • Payload limit. Hearth’s effective payload cap is 64 KiB minus the Kit’s header. The 1 MiB figure is the whole envelope on the Hearth side, and above it the hub drops the connection. A provider should declare its maximum payload and send should fail before the wire when it is exceeded. This is not built: PeerProvider has no member for a payload maximum today, so the app passes its limit to PeerJson.fits and encodeWithin.
  • Echo suppression. The hub delivers a broadcast back to its sender. Drop frames whose from.device and from.instance are this copy’s.
  • Its own correlation ids. The hub’s message id is not a safe key for matching replies. The Kit’s rid plus (peer, rid) matching is already independent of it, and a provider must not rely on the transport’s ids.
  • Deduplication by message id across live delivery and catch-up, liveness by a heartbeat sent no more often than every 30 seconds (the hub’s idle timeout is 90 seconds, and it caps publishes per hour per connection and per account), and reconnect.
  • Topics. The stock hub’s topic grammar rejects app-scoped topics. The Hearth tests carried app traffic on the stock topics, set payload_type = ak.app/<app>, and filtered at the receiver. That is a filter, not access control.

Two things are covered here: how to test an app built on the Kit, and how to run the App Context Kit repository’s own test suites.

The Kit is built so that an app’s tests need no network, no real home directory and no Venue. Two settings do that, and both are ordinary environment variables:

  • Scratch (APP_CONTEXT_SCRATCH) puts every directory and the roster under one throwaway folder, so a test never touches real data.
  • Mock (APP_CONTEXT_MODE=mock) replaces Venue with an in-memory fake and peers with an in-memory fake network.

Part 1 is for app authors. Part 2 is for working on the Kit itself.

Part 1: testing an app

Pass the environment in; do not read the machine’s

AppContext.open takes env:, platform: and home:. When you pass env, nothing from the real process environment is read, so a developer’s own APP_CONTEXT_* variables cannot change a test. The Dart test in docs/examples/dart_cli/test/kit_test.dart opens every context like this:

final env = {'APP_CONTEXT_MODE': 'mock'}; // the scratch directory is added per test

Future<AppContext> launch(AppManifest m, [Map<String, String> more = const {}]) =>
    AppContext.open(m, env: {...env, 'APP_CONTEXT_SCRATCH': scratch.path, ...more}, announce: false);

announce: false keeps the test out of the roster. scratch is a temporary directory made in setUp and deleted in tearDown:

late Directory scratch;
setUp(() => scratch = Directory.systemTemp.createTempSync('app-context-example-'));
tearDown(() => scratch.deleteSync(recursive: true));

The fake Venue

In mock mode, ctx.venue is a FakeVenue. It has one node and a capacity (the fakeCapacity parameter of AppContext.open, default 1), refuses a hold with doesNotFit when it is full, and logs each call. refuseNext(n, {kind}) makes the next n holds refuse whatever the capacity, so a wait-and-retry loop can be tested without arranging a full node. This test is from kit_test.dart:

test('mock mode gives a fake Venue that can be made to refuse, so a waiting loop is testable', () async {
  final ctx = await launch(manifest);
  final venue = ctx.venue as FakeVenue;

  const need = VenueNeed(name: 'job', contractClass: 'container.run.v1');
  final result = await venue.withHoldWaiting(need, (hold) async => 'done',
      maxWait: const Duration(seconds: 5), retryEvery: const Duration(milliseconds: 2));

  expect(result, 'done');
  expect(venue.log, ['hold job', 'hold job', 'hold job', 'start job', 'release job']);

Use a small retryEvery in tests. withHoldWaiting counts waiting in naps rather than reading a clock, so it behaves under fake time. To test against a Venue that answers in particular ways without a socket, implement DaemonTransport (one send method and one close) and pass it as transport:. The App Context Kit repository’s own tests do this in dart/app_context_kit/test/support/fake_transport.dart.

The fake peer network

Peers are off unless the manifest lists "peers" in kits. In mock mode, ctx.peerHub and ctx.startPeers use an in-memory network. Give two contexts the same FakePeerNetwork and they find each other. Nothing touches the real network or the disk. This test is from kit_test.dart; Listener is a small AppCoordination defined in the same file, which records the messages it gets:

test('two copies of an app find each other on one fake network and exchange a message', () async {
  final peerManifest = AppManifest.fromJson({'id': 'dev.example.hello', 'name': 'Hello', 'version': '0.1.0', 'kits': ['peers']});
  final network = FakePeerNetwork(); // pass the same network to both copies
  final laptop = await launch(peerManifest, {'APP_CONTEXT_DEVICE': 'laptop'});
  final phone = await launch(peerManifest, {'APP_CONTEXT_DEVICE': 'phone'});

  final listener = Listener();
  final laptopHub = laptop.peerHub(Listener(), network: network);
  final phoneHub = phone.peerHub(listener, network: network);
  await laptopHub.start();
  await phoneHub.start();

  for (var i = 0; i < 100 && laptopHub.readyPeers.isEmpty; i++) {
    await Future<void>.delayed(const Duration(milliseconds: 20));
  }
  expect(laptopHub.readyPeers, isNotEmpty);

  await laptopHub.broadcast(PeerJson.encode({'text': 'hi'}), kind: 'greeting');
  for (var i = 0; i < 100 && listener.received.isEmpty; i++) {
    await Future<void>.delayed(const Duration(milliseconds: 20));
  }
  expect(listener.received, ['laptop: {text: hi}']);

  await laptop.close();
  await phone.close();
});

Set APP_CONTEXT_DEVICE per copy so the two have different device names; the instance ids are random. The conformance fixtures

The fixtures are the contract in executable form. spec/conformance/manifest_cases.json has one case per manifest rule (valid and invalid), and spec/conformance/context_cases.json has one per directory or mode rule: given a manifest, a platform, a home directory and an environment, the expected directories, roster, scratch flag and mode. Both implementations load the same files:

  • Dart: dart/app_context_kit/test/conformance_test.dart
  • Rust: rust/tests/conformance.rs

The files are generated, not written by hand. tools/gen_fixtures.py spells every expectation out from templates, and never asks an implementation what the answer should be. The two-process test

Every peers test except this one runs inside one process. dart/app_context_kit/test/peers/two_process_test.dart starts each hub in its own operating-system process (two_process_worker.dart), over the loopback provider and one shared temporary directory. Two copies of one app and account find each other, exchange hello and admit (ready on both sides), send, broadcast and request/reply. A third process with a different app id and a fourth with a different account saw no peer event and no message in over 600 ms, and neither appeared in the others’ peer lists. A graceful quit is lost with the reason goodbye, and the announcement is gone.

It also kills one process with kill -9 to see what a dying process looks like to its neighbour, and prints the numbers it measures: how long the survivor takes to see the peer lost, and how long the dead copy’s announcement file stays behind. Run it with -r expanded to read them. APP_CONTEXT_GHOST_SECONDS (default 12) sets how long the survivor is watched after the kill. This variable is read by the test only; the Kit does not read it. Architecture

This page explains how the App Context Kit is put together: the layers, what happens when an app starts and stops, how two copies of an app connect, and how the spec, the shared test fixtures and the two implementations fit together.

The Kit gives one running app a root object, AppContext. An app gets its identity (the reverse-DNS id in app.json), its directories, its settings, a test mode, a presence entry in a shared roster, a session with a resource broker, and an opt-in way to find and talk to other copies of itself.

What to notice. Every exit path funnels into one shutdown that closes the context at most once; a second signal gets the same future instead of a second close.     A->>B: kit.hello (nonce, app hello)

Source: the protocol comment at the top of hub.dart, checked against _onHello, _onAuth and _checkReady.

What to notice. Only the copy with the lower PeerId dials, so two copies never open two links; the other side waits for the incoming link. That works only if discovery is symmetric, which it is for both built providers. “Ready” needs two things on each side: your admit said yes, and the other side’s kit.ready arrived. A link that is not ready after 5 seconds is dropped. A kit.reject marks the peer rejected on both sides, and it is not redialed until the provider withdraws and announces it again.

Why these boundaries

The Kit does not interpret payloads. The same hub carries three very different meanings in the demo apps: a signal (stopwatch), replicated notes with a conflict rule (notepad), and handing a game to another copy (minesweeper). Adding coordination to those three apps changed no file under dart/app_context_kit. If the Kit knew what a message meant, the first app whose meaning was different would have needed a Kit change. Keeping it opaque also means the Kit has nothing to get wrong about your data, and nothing in your data can confuse it: the Kit parses its own header and passes the payload on untouched.

The core avoids Flutter. Closing an app cleanly on window close or quit needs Flutter’s lifecycle, and starting needs its asset bundle, so those live in the companion package. Everything else runs under plain dart test with no engine. The core test suite (365 passed, 7 skipped) runs in about half a minute, and the peers logic runs as a headless process; the three demo apps that use peers each have a tool/peer_probe.dart that runs the app’s own coordination code without a window. The same boundary is what makes a second implementation possible: the Rust crate follows the same spec without touching Flutter.

One spec, with shared fixtures. A written spec alone lets two implementations drift. The fixtures turn the pure parts of it into data that both languages must pass, and the rule that the fixture wins keeps the prose honest. The fixtures are generated from spelled-out expectations, so a bug in one implementation cannot leak into the expected answer.

The second implementation found things the first could not. The Rust crate passed all 41 fixtures that existed when it was first written, and still disagreed with the Dart core on several behaviours that no fixture covered. Among them: how a root path joins (/ plus an id gave //id in Dart), whether a trailing backslash on a Linux path is trimmed, and whether a later set() may overwrite a config file that was found damaged (Dart did; Rust refused until the file is set aside). Each became either a spec decision, a fixture, or a per-language test: the fixture set grew from 41 to 61 cases. Those cases came from comparing the two implementations, not from reading either one alone.

Apps do not edit the Kit. A demo app that needs something the Kit lacks writes it under lib/kit_gaps/ with a // KIT GAP: comment. The line count of those directories is the measurement of what the Kit is missing; the ledger is kept with the demo apps in The Kit Book.

The Dart real-daemon tests (5) and TLS tests (14) passed against throwaway daemons when this page was first written; they skip without one, so the run for this page did not exercise them.
  • All six demo apps were built with flutter build macos --debug and launched during development. Cmd-Q and SIGTERM close the app cleanly (the roster entry is removed and Venue holds are released). Recorded in notes taken at the time; not re-run for this page.
  • Two real processes find each other over loopback, exchange messages, and see each other disappear after kill -9 (the link drop is seen in milliseconds; the peer is withdrawn in about 3.5 seconds). Tested in dart/app_context_kit/test/peers/two_process_test.dart; it passed in the full run for this page.
  • A copy killed with kill -9. The surviving copy sees the link drop at once (about 3 ms) and withdraws the dead copy’s announcement 3.5 to 3.8 s later (3.5 s on macOS, 3.8 s on Linux). Before the announcement carried a heartbeat the picture was worse: the survivor that had dialled gave up after 10 failed dials (about 31 s) but left the dead copy listed as found for ever (watched for 45 s); a survivor that never dials never learned the announcement was dead at all; and a restarted copy with the same device id appeared beside the ghost. The fix is in dart/app_context_kit/lib/src/peers/loopback_provider.dart: each provider rewrites its announcement file every second with a wall-clock beat; a file whose last beat is older than 4 s is not offered, and a peer already known from it is withdrawn (the hub then reports the final lost and stops dialling); a file older than 60 s is deleted by whoever notices. Checking the announcing process id was rejected: it means nothing across process-id namespaces (containers), ids are reused, and Dart has no portable way to ask whether a pid is alive without starting a process. The cost is one small write per second per process. Not fixed: a brief found right after the first lost, which for a crash lasts up to the 4 s limit (a graceful quit has none), because the hub deliberately re-announces a copy that is still advertised.

What was not checked. Release builds of the demo apps on macOS (only one, notes_rust, was built in release mode). Signed or notarized builds. The red window-close button on a real window (Cmd-Q and SIGTERM were). Launching from Finder or the Dock (see below). The text on screen in a real window: the display was off for most of the runs, so UI behaviour was read from the widget tree and from the apps’ own code, not seen.

Environment variables do not reach an app launched from Finder or the Dock. APP_CONTEXT_MODE, APP_CONTEXT_SCRATCH, VENUE_TOKEN_FILE and the rest are read from the process environment. To use them, start the app’s binary from a terminal. For a normal launch, put the Venue token at <config>/venue-token and use config.json for settings.

The App Sandbox

Flutter’s macOS template turns the App Sandbox on. A sandboxed app sees a private HOME and TMPDIR inside ~/Library/Containers/<bundle id>/Data. Apple requires the sandbox for Mac App Store apps (that is Apple’s rule, not something verified here).

The sandbox changes what the Kit means:

  • Every directory in the table above moves into the container. Data lands under Data/Library/Application Support/ID/, and the default roster is Data/tmp/app-context-roster. Each app has its own, so the default roster is no longer shared between apps.
  • APP_CONTEXT_SCRATCH and other overrides that point outside the container fail.

Today the demo apps (in The Kit Book) are mixed: the calculator, minesweeper and notepad have the sandbox on; the launcher, render-queue and stopwatch have it off (their entitlement files say app-sandbox is false). The reason is that no sandbox-on setup was found that works for all of them; see the roster row below.

How these results were obtained: copies of the built debug apps were re-signed ad hoc (no team ID) with the entitlement variants below, launched by running the binary directly, and observed through the container directory, the system log, and the widget tree. No entitlement file in the demo apps was changed by that work. These results come from notes taken at the time and were not re-run for this page.

Packaging checklist

For shipping an app that is built on the Kit. Each line says what to do and where it was observed to matter.

  1. Make the ids agree. Run dart tool/check_identity.dart <app dir> (from dart/app_context_kit_flutter). It must exit 0. Decide what a hyphenated manifest id does on each platform.
  2. Declare what you use. "kits": ["venue"] for Venue, "peers" for the peer layer. ctx.peerHub throws KitNotDeclared if peers is missing.
  3. Choose sandbox on or off per channel, and add entitlements for every capability you use (table above). Debug and Release are separate files. For peers, network.client and network.server in both.
  4. Put the Venue token where the app can read it. Under the sandbox that is <config>/venue-token inside the container, or VENUE_TOKEN. Not a path outside it.
  5. Provision the app with Venue before it ships. An app cannot register itself; see the Venue guide. Without that, the app runs on the local session and says so.
  6. Use short Venue leases. A killed app keeps its quota until the lease lapses.
  7. Start through AppContextKit.run (the companion package), so window close, Quit, SIGINT and SIGTERM all end in one ctx.close(). Test Cmd-Q and SIGTERM on the built app. kill -9 leaves a stale roster entry (hidden after 15 seconds) and any Venue holds until the lease lapses.
  8. Test in mock and scratch modes (APP_CONTEXT_MODE=mock, APP_CONTEXT_SCRATCH=<dir>) from a terminal; they do not reach a Finder or Dock launch.
  9. Do not use the loopback peer provider across a trust boundary. It has no encryption or authentication. It is for copies of an app on one machine, run by one user.
  10. Run on the real target. On Linux the Kit has headless container evidence only (see “What was not checked” under Linux above); on Windows and mobile it has none.

Design decisions

Reference page pulled from app-context-kit at commit 4797e81. Edit it in the Kit, not here.

Why the App Context Kit is shaped the way it is, what we tried instead, and what is still undecided. Each entry says what the evidence was, so you can disagree with the right thing.

Decisions that held

1. One written contract, two implementations, shared fixtures

The behaviour lives in spec/APP-CONTEXT.md. Dart and Rust both implement it, and both must pass the same fixtures in spec/conformance/. Why. The first implementation passed its own 41 fixtures on the first run, which proved almost nothing because the same author wrote the spec, the fixtures and the code. The Rust implementation, written from the spec text, passed the same 41 and still disagreed with Dart on about a dozen behaviours no fixture covered (what happens to / as a base path, which separator gets trimmed, what a name made only of a byte-order mark is, what happens when a named token file is missing…). Closing them took 20 more fixtures. The suite is the product; the prose is commentary. Cost. About twice the code in Rust as in Dart for the same behaviour, and a spec that must be kept honest.

2. The core is pure Dart; Flutter lives in a companion

The core package has no Flutter import, so it runs in a command-line tool, a server, or a test with no engine. Everything that needs Flutter (loading the manifest from an asset, exiting cleanly on window close or a signal, a mode badge, a notes banner, test helpers) is in app_context_kit_flutter. Why. In all six demo apps the same shims were written by hand (a 20 to 56 line exit hook was rewritten six times out of six). They are Flutter-shaped, so they belong in a Flutter package, and the rest should not pay for them.

3. The Kit never interprets an app’s payload

The Kit finds peers, checks scope, connects and routes. Meaning is the app’s, supplied through a five-method hook (channel, hello, admit, onPeer, onMessage). Why. The same hook expressed a live signal, a handoff and a conflict-resolving sync without the Kit knowing which was which. A Kit that knew about “notes” or “games” would have to be changed for every app. Cost. The hook is only just enough for live play, and for sync it is a small shell around a lot of app code. See what the hook does not give you.

4. Test modes are part of the Kit, not a test helper

APP_CONTEXT_SCRATCH=<dir> puts every directory (and the roster) under one temporary root. <PREFIX>_MODE=mock swaps Venue and peers for in-memory fakes. Both are in the contract and in the fixtures. Why. It was the part the demo apps liked most, and building them showed each app inventing its own way (two lookups for one override in one app, three different mock switches across three).

5. A damaged settings file is reported and never overwritten

Opening still works; set fails with a typed error until the app explicitly sets the damaged file aside. Why. An early defect: the first set() after a damaged file silently destroyed it, and a file that was not valid UTF-8 stopped the app starting. The rule is simple enough to be a fixture-level promise.

6. The roster has one file per running copy

roster/<id>@<instance>.json, with a heartbeat. Withdrawal removes only your own file. Why. With one file per app id, the first of two copies to exit erased the other’s presence. A viewer also needs to tell “crashed” (stale) from “never ran” (absent), so there is a scan that returns status, and a running() that hides the dead.

7. The Venue session hides “real”, “absent” and “fake”

App code calls the same methods against a real broker, no broker (a local session that says so in plain words), and a fake. Refusals are typed (doesNotFit, forbidden; everything else is unavailable), and a lease that is lost is reported, not swallowed. Why. It let render-queue run in all three modes with no branches in app code, and it made the real daemon’s behaviour (a refusal that arrives as a different HTTP code than expected) testable. Not hidden on purpose: registering an app with the broker. That needs an operator with authority (four manual steps today) and an app must not be able to grant itself access. The Kit documents the steps and stays out of them.

8. Peers are opt-in through the manifest

An app that wants peers lists "peers" in kits; asking for a hub without it is an error (KitNotDeclared). Why. It keeps the core small and gives the manifest’s kits list a real job. It was the only piece of evidence for “load Kits as needed” that the demo apps produced; none of them wanted runtime loading.

9. Several small rules in the peer layer, each from a failure

  • Scope is (account, app id). A peer of another app or account is never offered, never admitted, and a test proves an app B peer cannot receive app A traffic.
  • Only the lower peer id dials. Otherwise two copies open two links to each other.
  • seq is per link and restarts at 1. A gap is visible to the app as a jump; a bounded reorder buffer delivers in order and skips a gap that stays open.
  • A full outbox fails send; it never silently drops. Only the app knows what is safe to lose.
  • Announcements carry a heartbeat. A crashed copy’s announcement used to stay for 45+ seconds and cost ten failed dials; with a one-second beat, a beat older than four seconds is ignored and the copy is gone in about 3.5 seconds. (Process-id checks were rejected: they are unreliable across containers.)

10. Build a Kit piece when the second app copies it

The ledger: shim code across the six apps was 727 lines, 330 after the first migration, 777 after coordination was added (it rose, because every app wrote the same peers helpers), and 164 after those helpers moved into the Kit. Calculator, minesweeper and render-queue ended with none. The remaining four helpers (a notification helper, a large-blob transfer, a manifest scan, a process check) each have exactly one user and stay in their apps.

What we deliberately did not build

  • Runtime Kit loading (BeOS add-ons). No demo app wanted it; Flutter builds are static anyway. Selection happens at build time and opt-in happens in the manifest.
  • A looper/handler message model like BeOS’s. Dart and Rust each have an event loop; a third one would not map onto both.
  • A sync engine. The notepad’s sync is about 700 lines of app code because what to do on a conflict is a product decision. A shared engine would have to make it for you.
  • Launch, quit and focus from the launcher. A file roster can say who is running; it cannot ask an app to quit. A control socket per app is one possible design; it is not built.
  • Authentication. The Kit scopes by account and app id and says so loudly; it does not prove either. See below.

Still open

App Context Kit: the app context specification (v0.1)

Reference page pulled from app-context-kit at commit 4797e81. Edit it in the Kit, not here.

This is the contract both implementations (Rust in rust/, Dart in dart/app_context_kit/) must satisfy. It is checked by the shared fixtures in conformance/. If an implementer finds the text ambiguous, that is a finding: write it down (as an issue or a note) and do not silently pick; the fixtures win over the prose.

Everything here is a pure function of its inputs (no I/O), so both languages can be tested without a filesystem.

1. The manifest (app.json)

JSON, not YAML, on purpose: it avoids choosing a Rust YAML library for now. Whether the real thing is YAML is an open question.

{
  "id": "com.slashbuilder.demo.calc",
  "name": "Calculator",
  "version": "0.1.0",
  "kits": ["venue"],
  "envPrefix": "CALC",
  "venue": { "mode": "auto", "consumer": "calc" }
}

Fields: id, name, version required. kits optional (default []). envPrefix optional. venue optional.

Validation, checked in this order; report the first failure only, as these codes. A field that is present as null is present and invalid (kits: null is bad-kits). Every pattern must match the whole string: a trailing newline fails (this matters to implementations whose $ also matches before a final newline).

ordercoderule
0anot-jsonthe source text is not valid JSON (only for parse(text); a parsed value skips this)
0bnot-objectthe JSON is not an object (an array, a string, null…)
1bad-idid missing or not matching ^[a-z][a-z0-9-]*(\.[a-z][a-z0-9-]*)+$ (reverse-DNS, at least two segments)
2bad-namename missing, null, not a string, or empty after removing ASCII whitespace (space, tab, CR, LF). Other characters, including U+FEFF, count as content
3bad-versionversion missing or not matching ^\d+\.\d+\.\d+$
4bad-kitskits present but not a list of strings, or a name not matching ^[a-z][a-z0-9-]*$
5duplicate-kitthe same kit name twice (checked only after every name passed rule 4)
6bad-prefixenvPrefix present and not matching ^[A-Z][A-Z0-9_]*$
7bad-venuevenue present but not an object, or venue.mode not one of auto, on, off, or venue.consumer present and not matching ^[a-z][a-z0-9-]*$

Defaults after validation: venue.mode = auto; venue.consumer = the last segment of id; env prefix (below).

2. Resolution

Inputs: manifest, platform (linux, macos, windows), home (string), env (string map). Outputs: prefix, dirs.{data,config,state,cache,runtime}, roster (a shared directory), scratch (bool), mode (real/mock).

Prefix: manifest.envPrefix, else the last segment of id, upper-cased, with every character outside A-Z0-9 replaced by _. (render-queue becomes RENDER_QUEUE.)

Path joining: on linux and macos join with /, on windows with \, whatever the host is. Before joining, a trailing separator on an input base (for example TMPDIR=/var/T/) is dropped; the separators are those of the target platform only (/ on linux and macos; both / and \ on windows), so a trailing \ on a linux base is kept. A base that is only a separator (/) is not reduced to nothing: joining / and ID gives /ID, never //ID. Values used verbatim (overrides, below) are never trimmed.

Platform defaults (ID is the manifest id):

(On windows, a missing LOCALAPPDATA, APPDATA or TEMP is the error missing-env, but only if a default that needs it is actually used: a directory fixed by an override or by scratch needs none.)

Overrides, highest priority first, for each directory kind K in DATA, CONFIG, STATE, CACHE, RUNTIME:

  1. <PREFIX>_<K>_DIR: used exactly as given (no id appended, no trimming).
  2. Scratch: if APP_CONTEXT_SCRATCH=S (non-empty), the directory is S/ID/<kind> with <kind> lower-case, and roster is S/roster; scratch is true. (Scratch joins with / on every platform.)
  3. The platform default.

roster has one override of its own: APP_CONTEXT_ROSTER_DIR, which beats scratch.

Mode: <PREFIX>_MODE, else APP_CONTEXT_MODE, else real. Allowed values real, mock; anything else is the error bad-mode. Only the variable that wins is checked: a garbage APP_CONTEXT_MODE is ignored when <PREFIX>_MODE is set. Error precedence: bad-mode is reported before missing-env. An empty string counts as unset, for every variable above.

3. Venue (not in the fixtures; needs a network or a fake)

(v0.1 changes to this section are in section 5.)

Reuse Venue’s existing variable names so nothing new is invented: VENUE_DAEMON (URL, default http://127.0.0.1:7878), VENUE_TOKEN, VENUE_TOKEN_FILE, VENUE_DAEMON_FINGERPRINT. Token lookup: see section 5, item 2 (a VENUE_TOKEN_FILE that is set but missing or empty is an error, never a fall-through). venue.mode: off never connects; auto connects if a token exists and the daemon answers /healthz, otherwise degrades to a local session and says so in description (the way a larger app words it: “GPU lease: local (Venue not configured)”); on fails to open if it cannot connect. In mock mode the session is always the in-memory fake. The Rust crate has no remote session: with a token found, auto gives a local session that says so (a warning) and on fails to open.

4. Lifecycle and roster (a minimal first version, not covered by fixtures)

AppContext.run(body): resolve, create the directories, write a presence file roster/<ID>@<INSTANCE>.json ({"id","name","version","pid","startedAt","heartbeatAt"}), start a 5-second heartbeat, open Venue, run body, then on exit or error delete the presence file, run the close hooks and close Venue. (Holds are released by withHold, which is the only thing that tracks them; a context does not release holds it did not take through withHold.) A presence file is stale when heartbeatAt is older than 15 seconds. This is the BRoster question: does it belong here, in Venue, or nowhere? The Kit ships the smallest version so the answer comes from use.

5. v0.1 decisions

Building the second implementation showed that two implementations can pass 41 fixtures and still disagree. These are the decisions that close the gaps it exposed. Items marked (fixture) are covered by conformance/*.json; the rest are behaviours each implementation must test itself.

  1. (fixture) The manifest, resolution and mode rules above, including the new codes and precedences.
  2. Token lookup (replaces section 3’s order). VENUE_TOKEN; else the file named by VENUE_TOKEN_FILE; else <config>/venue-token. If VENUE_TOKEN_FILE is set but the file is missing or empty, that is a configuration error and the lookup does not fall through to <config>/venue-token: auto degrades to a local session whose description names the problem; on fails to open.
  3. Config is never silently overwritten. A config.json that is not valid UTF-8 or not a JSON object is damaged. open reports it (problem) and still opens; set and save then fail with a damaged-config error until the caller explicitly sets the file aside (renamed to config.json.corrupt). get<double> accepts a whole number (JSON 3 reads as 3.0).
  4. close() is idempotent and isolates hooks. The second call does nothing. Every onClose hook runs even if an earlier one throws; after all have run, the errors are raised together. Venue is closed last.
  5. Roster instance id. Each opened context draws a random 8-hex-digit instance id. The presence file is roster/<ID>@<INSTANCE>.json and carries an instance field; withdrawal removes only the context’s own file, so two copies of one app no longer erase each other. running() hides stale and unreadable entries (as before); scan() returns every entry with its status (live, stale, unreadable) so a viewer can tell a crash from “never ran”.
  6. Typed Venue answers. VenueRefused carries a kind: doesNotFit (HTTP 409) or forbidden (HTTP 403, including the live-hold limit). VenueUnavailable is everything else (transport failure, 401, 5xx). Venue gives no machine-readable reason for a 403 (the limit and other refusals share the code forbidden): a finding for the Venue project; until it does, forbidden is treated as not retryable.
  7. Holds the app can see. VenueSession.holds() lists this consumer’s own live holds (to find orphans after a crash). withHold no longer swallows renewal failures: the hold records them and the optional onLeaseLost callback fires; a failing release never replaces a successful body result (it is recorded on the hold).
  8. Fake capacity is a parameter of AppContext.open (fakeCapacity, default 1), not an environment variable.
  9. Notes carry a severity. ctx.notes is a list of {severity: info|warning|error, text}.
  10. Flutter. The core packages stay free of Flutter. A companion package supplies the pieces a Flutter app needs: loading app.json from an asset, a single guarded close on exit (window close, quit, SIGINT, SIGTERM), a mode badge and a notes banner.
  11. Coordination. See section 6.

6. Coordination between copies of the same app (the Kit manages, the app defines)

The Kit does not decide what coordination means. The app supplies a hook; the Kit finds, authenticates, connects and routes.

  • Scope key: (account, app id). A peer is another running copy of the same app id for the same account, identified by (device, instance).
  • Envelope: a Kit-owned header {account, app, channel, from:{device,instance}, seq, kind} and an opaque app-owned payload with an app-declared schema integer. The Kit never reads the payload.
  • Provider interface (how peers are found and carried; the Kit ships a fake and a loopback one): discover() (a stream of candidate peers), connect(peer), send(peer, bytes), and an inbound stream. Hearth and LAN providers are later work and need the Hearth protocol owners.
  • Hook (the app’s): channel; hello() (opaque, sent on connect); admit(peer, theirHello) returning accept, accept read-only, or reject; onPeer(peer, change) for found, ready, lost; onMessage(from, message).
  • Management interface (the Kit’s): a live peers view, send(peer, payload), broadcast(payload), request(peer, payload) with a timeout, and close().
  • Delivery: best effort with per-sender ordering by seq; anything stronger is the app’s.
  • Mock mode uses the fake provider so apps test coordination with no network.

6.1 As built in the Dart core (dart/app_context_kit/lib/src/peers/)

The first implementation departs from the sketch above in these ways. They are decisions to keep or reverse, not settled design.

  • admit may be async (FutureOr<Admit>): a pairing prompt or a storage lookup needs it. AppCoordination.attach(hub) (default no-op) hands the hook its hub. hello() must be JSON-encodable; the hook receives the decoded value.
  • One hub serves one channel, and admit is one answer per peer. An app with several facets (a timer, a notes sync, a game) uses one hub per facet or a mux hook that routes by kind prefix; the Kit has no per-facet admission.
  • Providers also have open(self) and close(); candidates carry available: false for withdrawal; rid (optional) correlates request and reply, whose reserved kind is kit.reply; the kit. prefix is reserved.
  • Only the lower PeerId dials, so two copies never open two links. seq is per link and restarts at 1 on a new link; a bounded reorder buffer (16 frames, 500 ms) delivers in order and skips a gap that stays open; the app sees loss as a jump in AppMessage.seq.
  • A full outbox fails send with PeerOutboxFull (256 messages or 8 MiB per peer) instead of dropping: only the app knows what is safe to drop.
  • acceptReadOnly only tags peer.readOnly; the decision is local and the other side is not told. A rejected peer is not redialed until the provider withdraws and re-announces it.
  • send completing means the transport took the frame, not that the peer applied it. No heartbeat or keepalive yet. No transfer for state over 1 MiB. No replay for a late joiner (use a version in hello() and let whoever is ahead push on ready).

6.2 What the Hearth integration changed (from testing against a local Hearth hub)

  • The app-scoped topic grammar is rejected by the stock hub (TOPIC_INVALID) and needs a one-file hub change (the hub’s topic module, about 60 lines). Until the Hearth protocol owners rule on it, carry app traffic on the stock topics with payload_type = ak.app/<app> and filter at the receiver.
  • The hub isolates accounts, not apps. Any device on the account can join any app’s topic, so the scope key is hygiene until a per-app credential and grant exist.
  • Provider payload limits differ. Hearth’s effective payload cap is 64 KiB minus the Kit header (the 1 MiB figure is the whole envelope and above it the hub drops the connection). A provider must declare its maximum payload and send must fail before the wire when it is exceeded; the 1 MiB cap in section 6 is the Kit’s outer limit only.
  • The Kit must do for itself on Hearth: Kit-owned correlation ids (the hub’s message_id is not a safe key) and request deadlines; echo suppression by from.device + from.instance (the hub echoes to the sender); dedupe by message_id across live delivery and catch-up; liveness by a no_retain heartbeat no more often than every 30 s (the hub’s idle timeout is 90 s and its hourly publish caps are 600 per connection and 6000 per account); reconnect.

6.3 Opting in, and who this copy is (ctx.peerHub)

  • Peers are an opt-in Kit. An app lists "peers" in app.json kits; ctx.peerHub(hook) throws KitNotDeclared otherwise. This is the first place the manifest’s kits list gates a capability.
  • Account: APP_CONTEXT_ACCOUNT, else config account, else local (a single-user machine with no household account yet; replaced by the real account when an identity service issues one).
  • Device: APP_CONTEXT_DEVICE, else config device; generated once (d- plus 8 hex digits) and saved, or ephemeral for the run if the settings file is damaged. Instance: the context’s instance id.
  • Provider by mode: an explicit provider; else in mock mode a fake network (pass one to share it between copies in a test); else the loopback provider over APP_CONTEXT_PEERS_DIR (default: the roster directory plus -peers). Hubs are closed with the context.

7. Additions (helpers the demo apps each wrote for themselves; additions only, nothing removed or renamed)

Evidence: the apps’ lib/kit_gaps/ files, identical across apps. Each addition below replaces a copy; the apps still compile against their old copies until they are migrated (new names were chosen so they cannot collide with the copies).

  • ctx.startPeers(hook, {network, options}) -> PeersHandle (core, peers/context_peers.dart). Builds AND starts a hub and never throws for a runtime condition. An unwritable peers directory or a provider that fails to open becomes handle.error ("peers unavailable: ..."), and the app keeps working alone. KitNotDeclared is NOT swallowed (a bug in the app). The handle: hub (null when unavailable; non-null while still opening; set back to null, and the hub closed, if opening fails, so handle.hub?.broadcast(...) is always safe), started (completes when open or failed, never with an error), error, isStarting, isRunning, changes (Stream<void>, broadcast: fires when the hub opens or fails and on every peer found/ready/lost; ends with the context). Closed with the context; a close that fails on a hub that never opened is not reported. Use ctx.peerHub for a custom provider or authenticator.
  • PeerJson (core, peers/peer_json.dart): encode, decode(bytes, {maxBytes}) (null for malformed, non-UTF-8 or oversized input; never throws), sizeOf, fits(value, maxBytes), encodeWithin(value, maxBytes) (throws PeerPayloadTooLarge, a PeerError), quiet(future) (a send nobody awaits), label(PeerId) (“laptop #3fa2”); and AppMessage.jsonBody. The Kit does NOT know a provider’s payload cap: the app passes the limit (Hearth: 64 KiB minus the Kit header). No JsonMessage {kind, v, body} envelope was built: all three apps use the Kit envelope’s own kind and schema and put only the body in the payload, so a second envelope inside the payload has no user.
  • VenueSession.withHoldWaiting(need, body, {required maxWait, leaseSeconds, retryEvery, renewEvery, cancel, onWaiting, onLeaseLost}) (core). Retries a doesNotFit (409) refusal; retries forbidden (403) only while holds() shows this consumer still has live holds of its own; gives up after maxWait (counted in naps of retryEvery, not read from a clock) with the LAST refusal; maxWait: Duration.zero is withHold. cancel (a Future) ends the wait at once with HoldWaitCancelled; a hold granted in that instant is released. Only the refusal of the hold is retried, never an error from body, never VenueUnavailable. withHold now shares its post-grant part (_runHeld) with it; behaviour unchanged. FakeVenue.refuseNext(n, {kind}) makes the fake refuse n times. VenueRefused.plainReason unwraps the daemon’s error.message. The 403 rule is a heuristic and has a known failure. The real daemon answers its per-consumer live-hold limit with 403, and also answers a missing grant or an observer token with 403, with the same code forbidden. A consumer that holds something and is refused 403 for lack of a grant waits maxWait for nothing before it gets the real refusal. Finding for the Venue project: give “over the live-hold limit” a machine-readable reason (or its own status); then drop the heuristic. Verified against the real daemon (consumer calc, limit 3): waits while it holds its own, is granted once one hold ends, gives up at maxWait with forbidden.
  • PeersIndicator (companion, package:app_context_kit_flutter/peers.dart): PeersIndicator.forHandle(handle, {extra}) or PeersIndicator(hub: hub, offlineReason:, extra:). Shows "This copy: <device> #<instance>", “Peers: N”, a chip per ready copy, “(K connecting)” and, when peers are unavailable, “Peers: off (peers unavailable: …)” with an icon. One live-region Semantics sentence; words and an icon, never colour alone. Same keys and texts as the apps’ copy. It is in its own library, not the app_context_kit_flutter.dart barrel, because an app that still has its own PeersIndicator imports both and would get an ambiguous name; re-export it from the barrel (additive) once the copies are deleted.
  • AppJsonFile / AppJsonRead / ctx.dataJson(name) (core): atomic write, read that tells missing from damaged, quarantine(). SessionSettings(store): a ConfigStore wrapper whose set keeps the change in memory for the session while config.json is damaged (readOnly says so). Both are the apps’ JsonFile / SessionConfig under names that cannot collide with them; the migration renames call sites.

7.1 Not built, and why

  • Large transfer (notepad/lib/kit_gaps/blob_pull.dart): not built: one user. What a Kit-level chunked transfer would need, if a second app wants it: (1) the provider declares its maximum payload (maxPayloadBytes) and the transfer sizes parts from it, instead of the app guessing a constant; (2) a pull protocol over request/reply (the only reliable primitive today): the receiver asks for part 0, 1, 2 … one reply at a time; (3) an opaque version tag on every part, pinned after part 0, and a restart (bounded attempts) when it changes mid-way; (4) a hard maxBytes enforced before allocating, and a bound on the part count taken from the sender’s first reply; (5) base64 accounting: payload bytes become base64 inside the Kit’s own base64, about 1.8x on the wire (24 KiB of text is a 44 KB frame); (6) typed outcomes: gone, too large, stale, and malformed-reply (the caller counts those) versus PeerError for a lost or silent peer; (7) a serving side (hub.serveBlob) that answers parts for bytes at a given tag; (8) progress callbacks, cancel, and request deadlines per part. Also unsolved: no acknowledgement and no replay (6.1).
  • Desktop notifications (stopwatch/lib/kit_gaps/notifier.dart): one user, and not an App Context Kit concern (a UI toolkit or the platform).
  • launcher gaps (manifest_scan.dart, pid_alive.dart): one user each. A scan of a source tree is not an install registry; pidAliveViaKill belongs with the roster (RosterRecord.processAlive or a control socket) and is only meaningful on the same machine and user.

8. Sharing one context between a Dart UI and a Rust core

A Flutter app with a Rust core is one process with two runtimes. If each side opened its own context, the app would announce itself twice (two roster files, two instance ids) and two code paths would write one config.json. So one side opens the context and the other adopts it.

  • The rule. The side that opened the context (normally the Dart UI: AppContext.open, or AppContextKit.run in Flutter) is the owner. It hands the other side a snapshot. The other side is the adopter: it calls AppContext::adopt(&snapshot) (Rust) and does not open a context of its own. An adopter does not announce: no roster entry, no heartbeat, no Venue session, no peers.
  • One owner per file. The owner owns config.json and the roster entry. The adopter only reads settings (the Rust crate’s ReadOnlySettings refuses every write) and owns the files it creates under data and state. It may create directories under those two and under no other. If the Rust core needs a setting changed, it asks the owner; the owner writes it.
  • The snapshot is JSON, produced by AppContext.snapshot() (Dart) or AppContext::snapshot() (Rust):
{ "schema": 1, "appId": "com.slashbuilder.demo.notes-rust", "instance": "0a1b2c3d", "mode": "real", "scratch": false,
  "dirs": { "data": "/abs/data", "config": "/abs/config", "state": "/abs/state", "cache": "/abs/cache", "runtime": "/abs/runtime" },
  "roster": "/abs/roster" }

instance is the owner’s 8-hex-digit instance id; the adopter has none of its own. mode is real or mock. Every path is absolute (a relative APP_CONTEXT_SCRATCH is made absolute by the owner). The snapshot has no secrets (no Venue token, no environment) and no file handles; it is a copy taken at one moment, not a live view.

  • Parsing is strict. First failure only, in this order: not-json, not-object, unknown-schema (any schema other than the number 1; a missing schema is missing-field), missing-field (the shape’s order; nested ones are dotted, dirs.data), unknown-field (the schema is the only versioning: an addition bumps it), bad-field (wrong type or pattern: appId is reverse-DNS, instance is ^[0-9a-f]{8}$, mode is real or mock, scratch is a bool, a path is a non-empty string), then relative-path. A path is absolute by its own syntax on any host: /x, \\server\share, C:\x, C:/x.
  • Fixtures. conformance/snapshot_cases.json holds snapshots written by the Dart test snapshot_test.dart (real contexts, except the Windows shape, which the host cannot open), each with the inputs it came from; Rust adopts each and asserts that its own resolve over those inputs gives the same directories, and the same instance. conformance/snapshot_negative_cases.json lists snapshots that must be refused, with the error code and field. They are separate from the 61 resolution and manifest cases.

site-check

Checks the site that make site built (it stops with a message if there is none) and prints one line per check. It uses only Python 3.

  • Publish folder: build/site-publish/ has a CNAME that holds exactly SITE_DOMAIN, an empty .nojekyll, an index.html, and the same pages as build/site/.

publish-site

Maintainers only. Removes the old build, runs make site and make site-check, then commits the contents of build/site-publish/ as one orphan commit (no parent) to a local branch gh-pages. The commit is built with a scratch index and no checkout, so main, your index and your working tree are never touched.

  • By default it is a dry run: it prints the commit, its file count, its CNAME, the repository’s visibility, the push it would have made, and why it did not, and exits 0.
  • It pushes only when all of these hold: PUBLISH=1; gh repo view says the repository behind origin is PUBLIC; the working tree has no uncommitted changes; and the current branch is SITE_REPO_BRANCH. The push is git push --force-with-lease=refs/heads/gh-pages:<what origin holds now> origin gh-pages:refs/heads/gh-pages. It never pushes any other branch.

linux-smoke

Builds every demo app for Linux in a container and launches each one under a virtual display. Needs Docker, make linux-smoke-image once, and the Kits fetched (make setup KITS=all while they are private; notes_rust is skipped without the Storage Kit like everywhere else). The repository is mounted read-only; each app is copied to the container’s own disk (without build/ and .dart_tool) and the host is never written to except build/linux-smoke/.

For each app: flutter pub get, flutter build linux --release (seconds and bundle size are recorded), then a launch under xvfb-run (1280x800x24, no window manager) with APP_CONTEXT_SCRATCH set, APP_CONTEXT_MODE=mock and the app’s own <PREFIX>_MODE=mock. It keeps the app up 10 s, takes a screenshot at 6 s, sends SIGTERM and records whether it was still running, the exit code, whether the roster entry appeared and was withdrawn, any Gtk/GLib warning and uncaught exception in the output, and the files the app wrote under the scratch directory. For calculator, stopwatch, minesweeper and notepad the first launch is driven with xdotool (a few clicks, and typing in the notepad) so there is something to save; a second launch on the same scratch directory then shows what survived. Finally two copies of stopwatch and of notepad run side by side in real mode with the same APP_CONTEXT_PEERS_DIR and different APP_CONTEXT_DEVICE values; the harness checks that each announced, that the two processes hold a TCP connection to each other, and, for notepad, that a note written into copy A’s folder arrives in copy B’s. The apps do not log peers, so the screenshot (each footer reads Peers: 1) is the other evidence.

Results: build/linux-smoke/results.md (a table, the environment and the details, including every warning line) and the screenshots build/linux-smoke/<app>-first.png, -second.png and -peers.png. build/ is ignored by git. Exit status is non-zero when an app did not build or was not running at 10 s.

What it proves and what it does not. It shows that the Linux runners build and that the apps start, draw, take mouse and keyboard input, write their state, survive a relaunch and exit on SIGTERM, headless under a virtual display, in a container, on one architecture (linux/arm64 on Apple silicon; linux/amd64 was not run). It is not a real desktop session (no window manager or compositor, no window-close click, no notification daemon), not a real GPU (software rendering), and says nothing about other distributions, Wayland, or X11 with a real server. The GTK accessibility-bus warnings it lists come from the container having no accessibility bus.

Publishing the website

The book is also a website, served at https://kits.slashbuilder.com from this same repository. This page says how the site is built and published, in what order the steps happen, and what is done by hand. The commands are described in Make targets.

How the site is built

make site turns book/ into a static website with mdBook. The output is in build/site/; nothing in it is committed to main.

  • Links out of the book. On GitHub a page can link to apps/, labs/ or CONTRIBUTING.md with a relative path. On the website those paths do not exist, so the build rewrites them, in a staged copy, to the file or folder on GitHub. The number of rewritten links is printed. Links inside the book are untouched.
  • Diagrams. The architecture diagrams are mermaid code blocks. GitHub draws them itself; on the website a pinned copy of the mermaid library, committed in tools/site/vendor/, draws them in the browser, in light or dark colours to match the page. The library is never fetched from the internet by the build or by a reader’s browser.
  • Search is mdBook’s built-in search: it runs in the browser from an index in the site.
  • Not indexed yet. Until the site is announced, every page carries <meta name="robots" content="noindex">. SITE_INDEXABLE=1 removes it.
  • Checks. make site-check verifies the built site: every internal link and #fragment resolves, the files GitHub Pages needs are there, the robots tag matches SITE_INDEXABLE, and the vendored library is the file whose checksum is recorded.

Preview it locally with python3 -m http.server -d build/site 8000.

How it is published

Publishing is a branch, not a workflow. The book does not use GitHub Actions (the Kits’ own repositories do: each public Kit runs its tests there). make publish-site builds and checks the site, then commits the built files as a single new commit with no history to a branch named gh-pages, and GitHub Pages serves that branch (“Deploy from a branch”). The commit is made without checking anything out, so main and your working tree are never touched.

Two files are added to every published commit:

  • CNAME, holding exactly the domain (kits.slashbuilder.com). With branch-based Pages, the custom domain lives in this file in the published branch. Because every publish replaces the whole branch, a publish without it would silently remove the custom domain from the site.
  • .nojekyll, an empty file, so that Pages serves the files as they are and does not run its own site generator over them.

The push is a force push (every publish is a new root commit) guarded by --force-with-lease, and it happens only when PUBLISH=1 is given and the repository is public. In every other case make publish-site builds the commit on a local gh-pages branch, prints what it would have pushed and exits successfully. Pages on the Free plan works only for public repositories, which is why a private repository is previewed locally.

The order of a launch. Every step that makes something public is a decision by the owner at the time, not a build step.

  1. Before anything flips: set the two contacts and commit the community files; make sure the notices match the vendored script; verify the domain for the organisation (step 1 below); run make go-public-check and read the table. The only rows allowed to be red are the ones the later steps clear: the Kit rename switch (b, c), the repository’s visibility (h).
  2. Make the Kits public, starting with the ones the book documents: create and publish each repository, then do the rename switch in kits.lock and re-pin.
  3. Make this repository public, then make go-public-check again: every row should now be ok.
  4. Publish the site and switch Pages on, then add the DNS record last (the steps below).
  5. Run the stranger test: make stranger-test (preview with STRANGER_DRY=1) clones the public repository with no GitHub login and runs make doctor, make setup and make test-fast there. Apps that need a Kit that is still private must skip with a message, not fail. Fix whatever breaks before announcing.
  6. Check every link in the announcement, then announce.

Each step has an undo (make the repository private again, remove the gh-pages branch, remove the DNS record), but making something public and then private again does not unpublish copies, forks or caches. The checks before the flip matter more than the rollback.

Going public, in order

The order matters. Nothing before step 5 changes what the public sees.

  1. Verify the domain for the organisation on GitHub (organisation settings, Pages, verified domains: add slashbuilder.com). GitHub shows a DNS TXT record to add at the DNS provider. This stops anyone else from claiming a name under the domain.
  2. Decide on indexing. Leave SITE_INDEXABLE=0 to publish a site that search engines are asked to ignore, or publish with SITE_INDEXABLE=1 when the site is ready to be found.
  3. Make the repository public, after make go-public-check shows no FAIL (the visibility row stays a warning until you do) and every Kit the book documents is public. This is a deliberate decision by the owner, not a build step.
  4. Publish: make publish-site PUBLISH=1, from a clean main. Then in the repository settings, Pages: source Deploy from a branch, branch gh-pages, folder / (root). The custom domain field then shows the value read from the CNAME file; do not clear it.
  5. Add the DNS record last: a CNAME record for kits pointing at the organisation’s github.io name, set to DNS only (no proxy) so GitHub can issue the certificate. A name that points at GitHub before anything claims it is how subdomains get taken over, which is why the record comes after steps 1 and 4.
  6. When the certificate is ready (Pages shows it), tick Enforce HTTPS.

The Kit rename and the pin

The Application Kit was renamed App Context Kit before going public. Its repository, slash-builder/app-context-kit, was created from the reviewed release candidate: the candidate is one commit with no parents, pushed as it is, so the commit id the repository starts from is the commit id this book already pinned. kits.lock names that repository and that commit. Until the repository is public the line is marked private.

At release, before step 3 above:

  1. Make slash-builder/app-context-kit public, then switch on what a private repository on the free plan cannot have: private vulnerability reporting, branch protection on main, and required reviewers on the release environment.
  2. In kits.lock, mark the app-context-kit line public. If the release candidate had to change, re-pin (make lock KIT=app-context-kit) to the commit the repository starts from.
  3. Run make clean-all && make setup, make docs-pull, make docs and make check-public. make docs-catalog then records the new repository’s visibility.
  4. Run make go-public-check. Rows b1 to b4 and c1, c2 check this switch: they refuse a kits.lock URL that does not end in the Kit’s name, a leftover rename comment, an old spelling, and a Kit whose repository or pinned commit does not answer HTTP 200 without a login. tools/go-public-allow.txt may never allow kits.lock.

What is manual

Everything on the list above except building and committing: domain verification, making the repository public, switching Pages on and choosing the branch, the DNS record, and the HTTPS setting are all done by a person in the GitHub and DNS settings. The tools in this repository never change a GitHub setting or a DNS record, and neither do make go-public-check and make stranger-test (the second only clones).

To take the site down, remove the DNS record first, then switch Pages off.

Glossary

The words these pages use, in alphabetical order.

Admit. The hook method that decides whether a peer may join an app’s coordination: accept, accept read-only, or reject.

App id. An app’s reverse-DNS name, such as com.slashbuilder.demo.notepad, set in its manifest.

App Context Kit. The Kit that is the root namespace for one running app: identity, directories, settings, modes, a roster entry, a session with a resource broker, and an opt-in way to find other copies of the app.

Candidate. A UI component proposed for the shared interface Kit, built from what several apps duplicate. See labs/interface_candidates. A candidate marked THIN has fewer than three real users.

Context. What an app receives from the App Context Kit when it starts: its directories, settings, notes for the person, session and peers. In Flutter, AppContextScope.of(context).

Core (role). In kits.lock, a Kit this book documents and whose own tests run in make test. The other roles are app-dep (needed by another Kit to build; fetched, not tested here) and reference (documented but not needed to build the apps).

Fetch. Downloading a Kit at its pinned commit into .kits/ with make setup or make fetch. No git is needed.

Hold. A reservation on a shared machine’s resources, taken from the Venue for the length of a job and released afterwards. A hold lasts for a lease; a crashed app keeps its hold until the lease runs out.

Hook. The five small methods an app supplies to say what coordination means for that app: channel, hello, admit, onPeer and onMessage. The App Context Kit finds and connects copies and routes messages; it never reads a payload.

Kit. A focused piece of SlashBuilder’s platform that owns one job. See the introduction.

Kit gap. Code an app wrote itself because a Kit lacked it. By rule it lives in the app’s lib/kit_gaps/ with a // KIT GAP: comment, and the line count of those folders measures what the Kits are missing.

Manifest. An app’s app.json: id, name, version, the Kit features it uses and its Venue settings.

Mock mode. A mode, switched on with APP_CONTEXT_MODE=mock, in which the outside world is replaced by in-memory fakes. Together with scratch mode (APP_CONTEXT_SCRATCH=<dir>, which puts every directory under one folder) it lets tests run without touching real files.

Peer. Another copy of the same app, on the same account, that the App Context Kit found and connected to.

Pin. The commit of a Kit that this repository uses, recorded in kits.lock. make lock shows how to move it.

Probe. A small program that exercises one thing and prints what happened. The apps’ tool/ folders hold probes that run an app’s own coordination code without a window. Probes of other Kits run in a private repository; the book carries only a summary.

Refusal. A typed answer from the Venue saying it will not grant a hold, for example because the app already holds its limit.

Roster. The set of presence files, one per running copy of an app, that lets apps (and the launcher demo) see who else is running on the machine.

Venue. The resource broker: a daemon that grants and tracks holds on a machine’s resources.
